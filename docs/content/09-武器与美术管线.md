## 1. 武器设计原则（先定规则，再填数值）

1. **TTK 锚定快节奏**：筏上 1v1 的击杀时间目标 **4–8 秒**。太快（<2s）→ 新手进局即死、8 分钟局变成互相偷人；太慢（>12s）→ 打不死人，最后 3 分钟分不出胜负。
2. **不做"数值碾压件"**：Legendary 武器只给**功能性优势**（控制、射程、效率），不给"两下秒人"的面板伤害。原因：最后存活制下，一件秒人武器会让滚雪球失控，与竞技公平冲突。
3. **武器差异化来自"与海上机制耦合"**，而不是 DPS 差异：能不能把人打落水、能不能拉人、能不能拆筏心、风暴里会不会失效 —— 这是海上玩法区别于普通 PVP 的地方。
4. **每件武器都要有明确反制**：火铳有装填窗口、鱼叉投空即劣势、弩炮依赖电力与弹药、钩竿对被拉者有 0.5s 免疫。没有反制的武器在长期服一定会变成"唯一解"。
5. **不禁用武器本体，只禁用合成配方** `[已批准 · 你的裁定]`：原版剑/斧/弓**物品仍存在、仍可使用**（避免"我的钻石剑变废铁"这种困惑，也给大厅与工具性用途留余地），但**移除其合成配方**且我们的 loot 表不掉落它们 → 局内实际能拿到的武备只有我们配平过的那一套。实现：datapack 配方移除 + 服务端 loot 白名单，**不做物品级禁用**。

## 4. 实现路径（ADR-001：客户端模组形态）

`[决策变更]` 玩家安装我们的 Fabric 客户端模组，因此**武器直接注册自定义 `Item`**，不再需要"原版载体 + CMD overrides"这套绕路（上一版本节作废，理由见 README ADR-001）。

| 需求 | 现路线 | 状态 |
|---|---|---|
| 武器身份与分类 | 注册表 id（`cww:cutlass` 等）+ `custom_data.cww_weapon_id`；**不靠 lore 文本** | 架构约定（保留，便于热改与排错） |
| 伤害 / 击退 / 耐久 | `minecraft:tool` 组件 + `minecraft:attribute_modifiers` + 我们的 `weapons.json` | `[已核实]` 组件层可覆盖（05 C11） |
| **攻速** | 客户端冷却条只是表现；**服务端记录上次有效攻击 tick，超频则减伤或拒绝并写审计**（05 C10） | `[待实测 S9]` |
| 外观（贴图 + 3D 造型） | 自定义 `Item` 自带 JSON 模型与贴图；复杂造型走**自定义 `ItemRenderer`** | `[待实测 S1]` |
| 手持动画 | 复用原版挥动动画；专属动作（鱼叉突刺、装填）可加客户端动画 | 可做项，非必须 |
| 右键交互（抛绳/开火/瞄准） | 自定义 `Item#use`/`usedOn` + 服务端状态机，不再受原版 use 语义束缚 | `[待实测 S2]` |
| 伤害权威性 | 战斗公式在**逻辑服务端**结算 → 我们的数值是权威 | `[已核实]` |
| 反作弊 | 客户端可被修改 → 频率与合法性一律服务端校验（05 R14） | 架构纪律 |

**保留的一条纪律**：外观与渲染失败**绝不能影响判定**。渲染只是表现，逻辑在服务端 —— 所以美术没画完也能先开服（占位模型顶上），**进度不被美术卡住**。

## 5. 平衡护栏（长期服必配，不是可选项）

1. **单局武器持有上限**：每人同时最多 1 近战 + 1 远程 + 1 工具，防止"六把武器轮流出"把资源优势变成不可逆碾压。
2. **武器不叠加稀有度收益**：Epic 弩不比普通弩多 3 倍伤害，而是多"控制/功能"（见 §2 表格设计）。
3. **弹药经济**：弩炮/火铳需弹药，弹药来自 Common 建材 → 长时间不开火是自然衰减，避免"蹲到决赛满弹药"。
4. **风暴事件必须削弱远程**：让近战/登船在事件中占优，形成节奏波动而不是远程单方面压制。
5. **数值审计**：埋点记录每件武器的**选用率 / 平均击杀 / 平均存活影响**，任一武器选用率 > 60% 或 < 5% 触发配平复盘（写进 07 §6.3）。
6. **禁止局外成长影响武器** `[已批准]`：外观解锁只能改贴图皮肤，不能改面板。

## 6. 美术资源管线（贴图 + 模型）

### 6.1 建模与贴图工具链（你已提供，本机已核实存在）

路径：`C:\Users\殷子竣\Desktop\AI建模\`，**本地运行，不依赖任何在线 API 或插件市场**。

| 组件 | 能力 | 对本项目的意义 |
|---|---|---|
| **`mcgen`** | `spec.json`（cubes / textures / resolution）→ Blockbench **`.bbmodel`**（贴图 base64 内嵌，单文件）+ 16×16 贴图 PNG + **等轴测预览**（自研 Z-Buffer 软光栅，支持半透明玻璃）+ `textures_sheet.png` 对照图 | 这就是我们的建模+贴图产线：**我写 spec.json，机器出模型、贴图与效果图**；你在 Blockbench 里打开 `.bbmodel` 精修 |
| 材质风格 | `metal` / `crystal` / `plank` / `stone` / `glass` / `water` + `emissive` 发光 + `rotation`/`pivot` + `group` 分组 | `plank`=木筏与木柄、`metal`=刀刃与炮、`crystal`+`emissive`=电鳗发电机、`water`=淡水/海水物资 —— **语义正好覆盖我们的素材** |
| 可扩展 | 在 `mcgen/pixel.py` 写 `f(n=16, seed=0) -> uint8[H,W,3]` 并注册进 `STYLES` | 后续加"布/绳索/锈铁"风格成本很低 |
| **`imggen`** | 本地 Stable Diffusion 文生图（DreamShaper 8；英文提示词；`--steps/--size/--seed/--cfg`） | 用于**概念图与底稿**，产出必须转成 16×16 像素风才能进游戏，不直接入库 |
| 校验 | `mcgen/validate.py` | 坏模型在进管线前就被拦下 |

### 6.2 生产流程（可批量、可重跑、可审计）

```
① 需求清单（§6.4）→ ② 我写 spec.json（尺寸/立方体/材质风格/发光/分组）
→ ③ python -m mcgen <spec.json> -o output/<名>      # 出 .bbmodel + 贴图 + 等轴测预览
→ ④ mcgen/validate.py 结构校验                       # 坏模型不进下一步

→ ⑥ 需精修 → 你在 Blockbench 打开 .bbmodel 调整后导出 MC 格式
→ ⑦ 入库 src/main/resources/assets/cww/… + 更新 art/manifest.json
→ ⑧ （可选）imggen 出概念图/宣传图，不直接进游戏

> **已核实的工具链缺口（必须补，约 0.5 人日）**：读 `mcgen/model.py` 与 `mcgen/cli.py` 确认 —— mcgen 目前**只输出 `.bbmodel`（Blockbench 工程）+ 贴图 PNG + 预览图**，**不输出 MC 游戏内格式**（block model JSON / entity geometry JSON）。两条补法：① 在 Blockbench 里手动导出（适合需要精修的实体模型）；② **我写一个 `spec.json → MC 模型 JSON` 的转换器**（cube 的 from/to/texture/rotation 与 MC block model 的 `elements` 几乎一一对应，适合批量物品与设施）。列入 M0：作为管线第 ③.5 步，避免"美术产线与模组资源之间靠手工搬运"。
```

**两套风格基准（你的裁定，写死进管线）**：
- **水世界系物品与设施**（海水过滤器、电鳗发电机、堆肥农场、医疗箱、筏心旗…）→ **仿已生成的 `电鳗发电机.bbmodel`** 的造型语言与配色（`mcgen` 的 `metal/crystal/plank` + `emissive` 那一套），保持原创内容辨识度。
- **自定义武器**（砍刀、长矛、鱼叉、火铳、弩…）→ **仿 Minecraft 原版武器贴图风格**（16×16、斜置造型、木/铁/钻既有配色、1px 深色描边），让玩家一眼看懂"这是把武器"。
- 两套共用 `art/palette.json` 基色（从**游戏内截图**采样），避免风格各走各的。ADR-001 后**物品、方块、实体三类模型走同一条 mcgen → Blockbench 管线**，风格一致性比零客户端路线好控制得多。
