# 03 地图与配置规范

> 对应你的 `服务端自定义化.docx`。那份文档给了字段雏形，本文把它补成可实现、可校验、可由地图作者自助维护的规范，并修正一处笔误。
> 标记：`[原方案]` / `[修正]` / `[新增·待批 A15]`（本文整节属于我补的规范设计，纳入 01 文档第 12 节的待批逻辑）。

---

## 1. 原方案内容与问题清单

`[原方案]` 字段：`minx / miny / minz / maxx / maxy / maxz`、`generate_y`（物资生成 Y）、`nogenerate: {}`（不刷新物资的坐标区域，可多个，可不填）；另有独立的 `大厅.json`（游戏结束后玩家出生位置）。

发现的问题（逐条给出处理）：

| # | 问题 | 处理 |
|---|---|---|
| P1 | `[原方案]` 中 `maxx` 的注释写的是"最低 x 坐标"，`maxy/maxz` 写"同上" | `[修正]` 语义改为 max = 上界（不含），并明确 AABB 的开闭区间约定 |
| P2 | 单个长方体无法表达"海域"（圆形才匹配等角出生 + 缩圈） | `[新增]` 引入 `arena` 概念：矩形外壳 + 圆形 playable 区域，两者并存 |
| P3 | 只有边界，没有队伍出生点、刷点、障碍、容量 | `[新增]` 补齐 `spawns / loot / hazards / limits` 四组 |
| P4 | 只有"刷/不刷"二值，无法表达"内圈品质更高" `[原方案]` 的核心 | `[新增]` 同心环带 `rings`，每环带独立 loot 权重倍数 |
| P5 | 没有配置版本、没有 ID，多地图会撞名 | `[新增]` `$schemaVersion` + 唯一 `id` + 命名规范 |
| P6 | 没有校验约定 → 配置写错就会崩服（长期服不可接受） | `[新增]` 加载期强校验、失败即拒绝该 arena 并输出可定位错误，绝不让服务端崩溃 |
| P7 | 一个 JSON 只描述一张图，规格预设（管理员按人数分配）无处挂 | `[新增]` 独立 `formats/*.json` 赛制预设，与 arena 解耦 |

## 2. 目录结构

`[原方案]` 要求在 `world` 文件夹内放 JSON，本文沿用（运维直觉好：换地图 = 换 world），并规定子目录：

```
<服务端根>/
├─ world/                        # 主世界（对局所在维度，MVP 固定 overworld）
│  └─ cww/
│     ├─ arenas/
│     │  ├─ default_sea.json     # 海域地图定义（本文 §3）
│     │  └─ coral_bay.json       # 后续多地图
│     ├─ formats/
│     │  ├─ quick_8min.json      # 赛制预设：队伍数/人数/时长（§4）
│     │  ├─ standard_12min.json
│     │  └─ big_15min.json
│     ├─ lobby.json              # 大厅定义（本文 §5）[原方案]
│     └─ _invalid/               # 校验失败的 arena 自动移入这里，不进内存
│        └─ 2026-11-04T09-30_default_sea.json
├─ config/crazywaterworld/       # 全局模组配置（数值表、开关）→ 见 02 文档
└─ data/cww/state/               # 运行时持久化（战绩、外观解锁）→ 见 04 文档
```

约定：
- 文件名 = arena `id`（去掉扩展名），必须 `[a-z0-9_]`，长度 ≤ 32；撞名时后加载者被拒绝并记日志 `[新增]`。
- 所有坐标一律**方块整数坐标**；方向用方块坐标，不用实体坐标（避免半格歧义）。
- 模组**只读** `arenas/` 与 `formats/`；`lobby.json` 也只读。写入型数据一律去 `data/cww/state/`，与地图作者可编辑的配置严格分离 `[新增]`（防止运维手改地图文件把运行时数据覆盖）。

### 2.1 内置默认图与"坐标—地形"配对 `[新增]`（2026-11-05 落地）

- 模组对 `world/cww/` **只读**这条纪律不变；内置默认图住在 **jar 里**（`data/nbw/arena/<id>.json`），
  只在 `<world>/cww/arenas/<id>.json` **不存在**时作为回退，两者同名时**本地优先**——
  这样地图作者的覆盖永远压过内置图，也意味着**改内置图不会生效**（`cww arena list` 会明说这件事）。
- 内置图有两张：`default_sea`（半径 140，生产形状）、`test_sea`（半径 60，测试夹具；
  它的 0.8R 等角环带只有 48 格，四队相邻仅 67 格，**满足不了 §3.1 出生间距要求，不能当正式赛用图**）。
- 默认海域的**地形**也随包发布，但是以**原版 datapack function** 的形式
  （`data/nbw/function/arena/<id>/build.mcfunction`），由管理员执行；模组自己一行写地形的代码都没有。
- **坐标与地形是同一份几何的两个产物**：`tools/gen_sea_function.py` 直接读 arena JSON 生成地形表。
  地图作者改了 `sea.radius`/`waterLevel` 却忘了重生成，运行时会由 `cww arena terrain <id>`
  读出"水位不符/海床不符/没有水"，不会静默把玩家扔进石头里。

## 3. Arena 定义（海域地图）

### 3.1 完整示例

```json
{
  "$schemaVersion": 1,
  "id": "default_sea",
  "dimension": "minecraft:overworld",

  "bounds": {
    "minX": -160, "minY":  40, "minZ": -160,
    "maxX":  160, "maxY":  72, "maxZ":  160,
    "axis": "y"
  },

  "sea": {
    "centerX": 0, "centerZ": 0,
    "radius": 140,
    "waterLevel": 62,
    "generateY": 63
  },

  "rings": [
    { "fromRadius": 0,   "toRadius": 28,  "lootMultiplier": 2.5, "tier": 3 },
    { "fromRadius": 28,  "toRadius": 56,  "lootMultiplier": 2.0, "tier": 2 },
    { "fromRadius": 56,  "toRadius": 91,  "lootMultiplier": 1.5, "tier": 2 },
    { "fromRadius": 91,  "toRadius": 140, "lootMultiplier": 1.0, "tier": 1 }
  ],

  "spawns": {
    "teams": [
      { "teamIndex": 0, "x":   0, "y": 63, "z": -112, "facing": "south" },
      { "teamIndex": 1, "x": 112, "y": 63, "z":   0,  "facing": "west"  },
      { "teamIndex": 2, "x":   0, "y": 63, "z":  112, "facing": "north" },
      { "teamIndex": 3, "x": -112, "y": 63, "z":   0,  "facing": "east"  }
    ],
    "auto": { "strategy": "equidistant", "minSeparation": 90 }
  },

  "loot": {
    "exclude": [
      { "minX": -20, "minZ": -20, "maxX": 20, "maxZ": 20, "reason": "center_ruins" }
    ],
    "candidates": "auto",
    "prefill": { "enabled": true, "count": 48, "radiusBand": [70, 140] }
  },

  "hazards": [
    { "type": "reef",  "minX": 40, "minZ": -60, "maxX": 70, "maxZ": -30 },
    { "type": "ruins", "minX": -20, "minZ": -20, "maxX": 20, "maxZ": 20 }
  ],

  "limits": {
    "maxRaftArea": 96,
    "maxBlocksPerRaft": 3200,
    "maxFacilities": 8,
    "buildYRange": [62, 80],
    "initialRaftSide": 4,
    "initialRaftBlock": "oak_planks"
  }
}
```

### 3.2 字段说明

| 字段 | 必填 | 含义 | 备注 |
|---|---|---|---|
| `$schemaVersion` | ✅ | 配置格式版本 | 加载器按版本做兼容迁移；不认识的版本直接拒绝 |
| `id` | ✅ | 唯一标识 | 用于命令、日志、战绩关联 |
| `dimension` | ⬜ | 对局维度 | 缺省 `minecraft:overworld`；预留多世界 |
| `bounds.minX/minY/minZ` | ✅ | 区域**下界**（含） | `[原方案]` |
| `bounds.maxX/maxY/maxZ` | ✅ | 区域**上界**（不含） | `[修正]` P1；约定半开区间 `[min, max)` |
| `bounds.axis` | ⬜ | 缩圈收缩轴 | 海域固定 `y` 无意义 → 实际缩圈是 XZ 平面圆形，此项为将来竖玩预留 |
| `sea.center* / radius` | ✅ | 圆形可玩海域与初始半径 | `[新增]` P2；`radius` = 黑海 P0 初始半径 |
| `sea.waterLevel` | ✅ | 海平面 Y | 筏体建造基准 |
| `sea.generateY` | ✅ | 物资生成 Y | `[原方案] generate_y`，明确为方块中心 Y（=63 表示 63.5 实际坐标） |
| `rings[]` | ✅ | 同心环带 → 物资品质梯度 | `[新增]` P4，落实 `[原方案]`"部分海域区块提高物资品质" |
| `spawns.teams[]` | ⬜ | 每队精确出生点 | 与 `auto` 二选一，见 3.3 |
| `spawns.auto` | ⬜ | 自动等角分布 | 由模组按队伍数计算，地图作者不用手改 |
| `loot.exclude[]` | ⬜ | **不刷新物资**的区域 | `[原方案] nogenerate`，保留语义但改名 + 加 `reason` |
| `loot.candidates` | ⬜ | `auto`（按水面自动找）或显式点位列表 | MVP 先 `auto` |
| `loot.prefill` | ⬜ | 开局前预铺漂浮物 | 落实"开局 0–2min 抢物资"节奏 |
| `hazards[]` | ⬜ | 障碍（暗礁/残骸），影响航行与战术 | 不阻断，只减速/卡位 |
| `limits.*` | ✅ | 建造与性能硬上限 | `[新增]` P3 + A14，TPS 与 grief 的保险丝 |

### 3.3 出生点：精确 vs 自动 `[新增]`
`spawns.teams` 与 `spawns.auto` 同时存在时，**以 teams 为准**，auto 仅在队伍数 > 已定义点数时补位。这样一张图能同时跑 2/3/4/6 队（对应你选的"管理员按在线人数分配"），不需要为每种人数单独写地图。

## 4. 赛制预设（formats）`[新增·待批 A12]`

与地图解耦，管理员开局时选择：

```json
{
  "$schemaVersion": 1,
  "id": "standard_12min",
  "teams": 4,
  "teamSize": 3,
  "minPlayers": 4,
  "duration": { "phases": [150, 60, 180, 180, 9999], "targetTotal": 720 },
  "border": {
    "stages": [
      { "at": 150, "radiusScale": 1.00, "damage": 0.0, "warn": 15 },
      { "at": 210, "radiusScale": 0.65, "damage": 0.5, "warn": 15 },
      { "at": 390, "radiusScale": 0.40, "damage": 1.0, "warn": 15 },
      { "at": 570, "radiusScale": 0.20, "damage": 2.0, "warn": 15 },
      { "at": 690, "radiusScale": 0.05, "damage": 4.0, "warn": 10 }
    ]
  },
  "loot": { "tierBias": "standard", "respawnIntervalSec": 22 },
  "events": { "pool": ["supply_rain", "storm", "black_sea_surge", "survivor_drift", "bounty"], "intervalSec": [150, 240] }
}
```

- `border.stages[].radiusScale` 相对 `arena.sea.radius`，因此**一张图可跑不同人数**（人少 → 用 quick 预设，圈更小）。
- 三档预设差异只写在 02 文档数值表里，本文只定结构。

## 5. 大厅定义 `[原方案]`

`[原方案]`：在 world 文件夹中生成一个 `.json` 保留大厅位置，填写游戏结束后玩家出生位置。
`[新增]`：大厅不只是"一个坐标"，它还是一个受控区域，补齐为：

```json
{
  "$schemaVersion": 1,
  "dimension": "minecraft:overworld",
  "spawn":  { "x": 0, "y": 80, "z": 0, "yaw": 0, "pitch": 0 },
  "bounds": { "minX": -24, "minY": 64, "minZ": -24, "maxX": 24, "maxY": 96, "maxZ": 24 },
  "enrollNpc":   { "x": 0, "y": 80, "z": 3 },
  "teamFlags":   [ { "teamIndex": 0, "x": -6, "y": 80, "z": 6 }, { "teamIndex": 1, "x": 6, "y": 80, "z": 6 } ],
  "spectateAnchor": { "x": 0, "y": 100, "z": -40 },
  "rules": { "pvp": false, "greifing": false, "hunger": false, "flyAllowed": false }
}
```

- `teamFlags` = 自主分队交互点 `[原方案]"玩家可自主分队"`；ADR-001 后做成**我们的自定义交互实体 + 专属分队界面**（见 04 §6）。
- `spectateAnchor` = 观战传送锚点（配合 01 §11 观战空投）。
- `rules` 让大厅行为与对局严格隔离，避免大厅变 PVP 场。

## 6. 加载与校验规则 `[新增]`（长期服最关键的一节）

### 6.1 校验清单（任一失败即拒绝该 arena）
1. JSON 语法可解析；`$schemaVersion` 受支持。
2. `min < max`（逐轴）；`bounds` 完全包含 `sea` 圆（`radius ≤ 到最近边界的距离`）。
3. `rings` 无空洞、无重叠、按半径递增、最后一段覆盖 `sea.radius`。
4. `spawns.teams[]` 点数 ≥ 所有 format 里最大的 `teams`；每个点在圆内且距中心 ≥ `radius*0.5`；两两间距 ≥ `minSeparation`。
5. `generateY` 在 `[minY, maxY)` 内且与 `waterLevel` 差不超过 2。
6. `loot.exclude` 区域不得覆盖 > 30% 可刷面积（否则物资密度不足，直接判无效）。
7. `limits` 全部 > 0 且 `maxBlocksPerRaft ≥ 100`；超上限的 raft 建造在运行时被拒绝而不是崩服。
   （现状 2026-11-06：`maxRaftArea` / `maxBlocksPerRaft` / `maxFacilities` 三项已真的接进建造判定，
   设施数还要再过一道"每 5 格甲板 1 位"的面积额度，见 `dev/M2-RESULTS.md` §3.12 与 §3.13。
   `initialRaftSide` 是**边长**（4 → 4×4=16 格甲板），校验水界 0..17，0=用默认值；
   它取代旧的 `initialRaftRadius`，因为 4×4 这种偶数边长用半径根本表达不出来。
   **`buildYRange` 仍未接入运行时**——它是世界 Y，而建造区要的垂直范围是"相对甲板几格"，
   见 `dev/M2-RESULTS.md` §3.12；**`buildYRange` 仍未接入运行时**——它是世界 Y，而建造区要的垂直范围是
   "相对甲板几格"，两者不是一个东西，硬接一定错。字段先保留，别指望它生效。）
8. `format.border.stages` 时间严格递增，最后一段 `radiusScale > 0`，`damage` 单调不减。

### 6.2 失败处理（务必按此实现，不允许"自动纠正"）

> ✅ **本节已端到端验证（2026-11-04）**：`ConfigService` + `/cww arena test|reload|list` + 19 个 JUnit 用例 + 真机演练。
> 演练结果：故意写入的坏 arena（圆超出 bounds、limits 低于下限、rings 有 1 格空洞、末段未覆盖半径）
> 被**拒绝加载并输出 4 条字段级错误**，文件自动移入 `cww/_invalid/2026-11-04T15-49-46_broken_sea.json`，
> `arenas/` 目录随即只剩合法图，**服务端全程存活、RCON 可继续驱动**。
- 校验失败的 arena → 移入 `cww/_invalid/`（带时间戳），日志输出**字段级**错误（`default_sea.json: rings[2].toRadius=91 与 rings[3].fromRadius=92 存在 1 格空洞`），服务端继续正常运行。
- **禁止**任何"猜测纠正"（例如自动补空洞、自动 clamp）。配置错必须显式暴露，否则地图作者永远收不到反馈，长期服的地图质量会不可控。`[我的硬性建议]`
- 提供 `/cww arena list|test|reload`（`test` 只校验不加载；`reload` 支持热替换，但**对局进行中禁止替换正在使用的 arena**）。

### 6.3 安全
- 路径只允许 `cww/` 下的固定子目录，文件名经过白名单过滤（拒绝 `../`、绝对路径、反斜杠），避免服务端任意文件读写。`[硬性要求]`
- 原子写入：所有写盘走 `.tmp` → rename，防止崩溃时留下半截 JSON。

## 8. 地图注册表 + 随机池 + 模板复制重置（2026-11-08，参照 RicordRailExpress）

> 用户裁决：**随机池 + 管理员可指定**（不做玩家投票）；**模板复制式重置（新增固定结构）**；
> **保持简单结算面板**（不做结算舞台）。本节记录落地后的实际模型。

### 8.1 地图注册表（单层，元数据写进 arena JSON）

不用参考项目的两层（注册表 + 实例）：我们把注册表元数据直接写进 arena JSON 顶层，
`world/cww/arenas/*.json` 的本地覆盖同样生效（与 §6 的覆盖规则一致）。

| 字段 | 类型 | 缺省 | 含义 |
|---|---|---|---|
| `displayName` | string | id | 显示名 |
| `description` | string | — | 描述 |
| `canSelect` | bool | true | 是否进入随机池 |
| `weight` | int | 1 | 随机池权重；`<=0` 不进池 |
| `minPlayers` / `maxPlayers` | int | 0 / -1 | 人数范围（-1 = 不限） |
| `formats` | string[] | 空 = 全部 | 该图支持的赛制 id |

### 8.2 随机池

`/cww start <format>`（不写地图）时，`ArenaPool.random(format, 报名人数)` 从池里按权重抽一张；
管理员写 `/cww start <format> <arena>` 仍可直接指定。池空时明确报错，**不回退默认图**。

### 8.3 模板复制式重置

`arena.reset` 段：

```json
"reset": {
  "resetTemplateArea": { "minX": 140, "minY": 62, "minZ": 140, "maxX": 147, "maxY": 69, "maxZ": 147 },
  "resetPasteArea":    { "minX": -4,  "minY": 62, "minZ": -4,  "maxX": 3,   "maxY": 69, "maxZ": 3   },
  "noReset": false,
  "mustCopy": true
}
```

- **模板区** = 永久保留的原始结构；**贴合区** = 每局实际使用的位置。
- 开局 READY 时 `MapResetService.begin` 登记复制，之后每 tick 复制 ≤8192 块（`onEndTick` 推进），
  避免一次性写几千块卡服——与参考项目「逐 tick 跑重置任务」同一思路。
- 模板用 `/cww reset buildtemplate` 建一次（内置函数 `nbw:reset/build_template`，落在模板区）。
- `noReset=true` 跳过；`mustCopy` 保留语义，当前实现就是全量复制。
- 本轮固定的结构是 `default_sea` 中心的「残骸平台」（8×8 石砖 + 四角断柱 + 箱子），
