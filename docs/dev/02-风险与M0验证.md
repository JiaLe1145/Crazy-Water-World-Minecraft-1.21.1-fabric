## 2. 关键问题与结论

> 本节初稿写于 M0 之前，10 条全是"未验证"。**M0 已给出 Q1–Q4、Q7 的结论**，逐条标注如下；
> 详细证据在 `M0-RESULTS.md` 与 `M0-TEST-PLAN.md`，本表只留判词与去向。

| # | 问题 | 为什么是生死线 | 结论 |
|---|---|---|---|
| **Q1** | **专用服务端是否可用？** | 我们是服务端玩法模组，Sable 若只能单机则方案作废 | ✅ **通过**。`runServer` 三方共存（nbw + sable + carpet）起服 1.4s 无异常，三个维度各建 Rapier 管线，UDP 通道 active。退路作废 |
| **Q2** | **玩家站在移动的 sub-level 上是否平滑随动？**（本次重做的起因） | 移动手感 | ✅ **通过**。`@t` 解析出筏 = 随动绑定生效；真人判定顺畅；抽帧复核人货不分离。**随动是 Sable 原生 mixin 做的，我们一行代码都不用写**（`ServerPlayerMixin.java:30-51`）。"停泊式玩法"退路作废 |
| **Q3** | **筏上容器/方块实体在移动中是否可交互、数据是否保留？** | 生产链 + 筏心全依赖这一点 | ✅ **通过**。移动中箱子可开可取放、数据没丢；筏上掉落物随船移动。装配时 BE 用 `saveWithFullMetadata`→`loadWithComponents` 随迁且**计入质量**（实测 25.0 = 49×0.5+0.5 吻合）。"设施改为实体承载"退路作废 |
| **Q4** | **建造（放置/破坏方块）能否作用在 sub-level 上？** | "收集物资强化木筏"是核心循环 | ✅ **通过**。滑行中放置的方块随筏移动、质量随之变化；破坏后质量回落。→ **"边航行边建造"成立**，"靠岸建造两段式"退路作废 |
| **Q5** | **性能：多筏 + 物理 + 12–18 人**的 TPS 与内存 | 长期服硬指标 | ⏭ **移出 M0**（无我们的代码时没有可测对象）。改在 M2 用 4–6 艘真实筏 + 回合逻辑压测。退路保留：限制筏体尺寸/数量，或改小局规格 |
| **Q6** | **与我们自己模组的共存**：Sable 的 mixin 会不会破坏我们的判定 | F2 明说兼容性差 | 🟡 **部分核实**。nbw + sable 2.0.6 + carpet 1.4.147 三方共存起服 1.4s 无异常、命令层与回合逻辑均正常响应；**完整回归在 Gate G1**。我们目前**没有注册任何 mixin**，真正的冲突面要到 M2/M4 注册方块与实体时才出现 |
| **Q7** | **API 可用性**：能否用代码创建/控制 sub-level | 决定调用层的可行性与工作量 | ✅ **通过**。命令树已从源码逐行定稿（12 个顶层子命令 + `@e@n@r@v@l@t@i` 选择器 + 修饰符），与客户端 Tab 补全双向对上；`SubLevelAssemblyHelper`/`PhysicsPipeline`/`SubLevelContainer` 的方法语义已读通。**"只能手动造船"的退路作废** |
| **Q8** | **竞技公平**：物理驱动的位置是否可被客户端利用 | 竞技服口碑底线 | ⏭ **移出 M0**，M2 与动力实现一起测（同规格筏航速方差 + 异常包重放）。默认策略不变：关键判定（伤害、圈内外、淘汰）全部服务端重算 |
| **Q9** | **存档与重启一致性**：崩溃/重启后 sub-level 是否完整恢复 | 长期服必然遇到 | ⏭ **移出 M0**，M2 集成期做（移动中强杀进程，核对筏体位置与 BE 数据）。已知风险点：`sub_level_velocity_retained_on_load=0.9` → 重启后筏会带 90% 速度"窜一下" |
| **Q10** | **版本锁死风险**：Sable 只支持 1.21.1，若上游停更或改 API | 我们把它当核心依赖 | 🔁 **持续监控**，不是一次性验证项。已知硬证据：构建期出现过 `Cannot remap ... class_1309` 警告（F14 风险实证），**换 MC 小版本时这类 remap 失败会变硬错误**。源码已留桌面副本，fork 冻结在 Shield 下允许（不得竞争性分发） |

## 3. 其它风险（非 Sable）

| ID | 风险 | 对策 |
|---|---|---|
| R1 | **玩法定义漂移**：一旦筏体行为由 Sable 决定，原方案里"划桨位移/筏心破拆/沉筏倒计时"可能要改 | 内容文档保留，但**每条玩法都标注"依赖 Sable 能力等级"**：A=直接可做 / B=需变通 / C=做不了要改玩法 |
| R2 | **拖局**（最后存活制固有） | 终局圈内持续掉血，而非加快缩圈 |
| R3 | **状态机制红线**：营养/水分/受伤不得单独致死 | 数值守住 + 回归用例 |
| R4 | **配置错误崩服** | 沿用旧计划的校验+拒绝加载+归档策略（`docs/content/03`） |
| R5 | **依赖链合规**：LGPL/MPL/Apache/PolyForm 混在一起 | `04-依赖与运维.md` 里逐条写清义务与打包方式 |
| R6 | **自动化并行开发冲突**（上一轮实际发生） | 自动化任务与人工会话**不得同时写同一仓库**；起服前先探端口；提交只按文件名 `git add` |

## 4. M0 验证清单（顺序即优先级，任一条失败就停下来汇报）

```
M0-1  依赖装配：Sable + 4 个前置模组 + Fabric 1.21.1 起服成功，不崩
M0-2  Q1 服务端可用性：runServer + runClient 能建 sub-level 并移动
M0-3  Q7 API：拿到"代码创建/移动 sub-level"的最小可用调用路径（含类名与方法名）
M0-4  Q2 手感：真人站上筏，连续移动 —— 平滑 / 可接受 / 不可接受（三选一，附视频）
M0-5  Q3 交互与保真：移动 100 格后容器可开、NBT 正确、设施数据在
M0-6  Q4 建造：在移动中的筏上放置与破坏方块是否正确生效
M0-7  Q5 性能：4 筏 + 物理 + 假人压测 TPS/内存
M0-8  Q6 共存：接入我们的注册表/命令/回合逻辑后回归无异常
M0-9  Q9 崩溃恢复：移动中强杀进程，重启后状态一致
M0-10 Q8 公平：异常客户端包重放，服务端仍权威
```

**M0 只做这件事，不写玩法功能代码。** 预计 5–9 人日（比旧计划低，因为不用自研引擎，但要读文档 + 试错）。

**Gate G0**：M0-1～M0-6 全绿才进 M1；M0-4（手感）由**你**判定，不接受我自己说"应该行"。

## 5. 失败时的决策树

```
M0-2 服务端不可用 ──→ 换 1.20.1 + Eureka/VS2（Apache/LGPL，许可更干净）
M0-3 API 不可用（只能手动造船）──→ 玩法重定义为"玩家自己造真船"，或退回自研离散移动
M0-4 手感仍不可接受 ──→ 木筏改为"停泊式"（建造/作战在停泊态，航行是过场），重新设计对局节奏
M0-5/6 交互或建造不成立 ──→ 生产链搬离筏体（岸上/浮岛设施），玩法结构改动，需你重新批
M0-8 与我们的代码冲突严重 ──→ 缩小我们的 mixin 面，或把冲突逻辑改为事件驱动
```
