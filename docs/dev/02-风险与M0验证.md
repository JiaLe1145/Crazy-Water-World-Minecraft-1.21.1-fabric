# 02 · 风险登记与 M0 验证清单

> 新计划的地基：**先证明 Sable 能用，再写任何玩法代码。**
> 标记：`[已核实]` = 有来源/实测支撑；`[未验证]` = M0 必须给出结论；`[退路]` = 不通过时的备选。

## 1. 已核实的 Sable 事实

| # | 事实 | 来源 |
|---|---|---|
| F1 | 定位是「**Interactive physics moving block structures**」库模组，提供 **sub-levels**：独立的动态位置与朝向里存放**正常 MC 的 chunk、实体与方块实体** | GitHub README |
| F2 | 官方自述「**an incredibly intrusive mod**」，大量 mixin，「**prone to extensive compatibility issues**」 | GitHub README |
| F3 | 内置 **Rapier 物理引擎**（Rust 原生库，`sable_rapier` 模块），含 sub-level 切分区域算法、浮动方块、专用 sub-level 渲染器 | GitHub README |
| F4 | 版本支持：**仅 1.21.1**，Fabric 2.0.6（17MB jar）；另有 NeoForge 分支 | Modrinth API |
| F5 | 许可证：**PolyForm Shield 1.0.0**——禁止的是"提供与该软件竞争的产品"，**不是禁商用**；分发必须把条款与 `Required Notice:` 一并传给下游；**不得再授权（sublicense）** | PolyForm 条款原文 |
| F6 | 运行依赖：Fabric API(Apache-2.0)、ImGuiMC(LGPL-3.0)、Veil(LGPL-3.0)、Forge Config API Port(MPL-2.0) | Modrinth 依赖解析 |
| F7 | 2.0.6 更新内容：修复「站在流体上的实体（如炽足兽）被 Sable 破坏」、调整「fabric 网络 mixin」 | Modrinth changelog |
| F8 | 存在官方 **Developer Wiki** 与 **Sable Companion**（给其他模组做兼容适配的官方项目） | GitHub README |
| **F9** | **`environment: "*"`** —— Sable 自带**服务端部分**，不是纯客户端模组（M0-2 的先决条件已满足，仍需实机证明） | 解包 `fabric.mod.json` 实测 |
| **F10** | **公开 API 面向模组作者**：`dev/ryanhcode/sable/api/{sublevel, sublevel.ticket, schematic, physics, physics.force, physics.constraint, physics.mass, physics.handle, physics.collider, physics.callback, entity, block.propeller, event, command, math, particle}` | 解包 jar 实测（2.0.6，17,162,518 字节） |
| **F11** | 力学接口粒度够用（力/约束/质量/碰撞体/句柄/回调）→ 「桨、帆、电鳗发电机推进」可以用它的力学语义表达，不必我们自己算位移 | 同上 |
| **F12** | 存在 `api/schematic` → **可用代码从方块集合创建 sub-level**，这是「开局发初始筏 / 结算销毁筏」的关键能力 | 同上 |
| **F13** | 自身基于 **Architectury**（跨加载器抽象）与 **Veil ≥4.3.2**（渲染），带 `assets/sable/pinwheel/shaders` 自定义渲染着色器；mixin 配置两套：`sable.mixins.json` + `sable-fabric.mixins.json` | jar 内 `architectury.common.json`、`fabric.mod.json` |
| **F14** | 依赖声明：`fabricloader >=0.16.9`、`java >=21`、**`minecraft 1.21.1`（精确锁，非 `~`）**、`veil >=4.3.2`、`fabric-command-api-v2`、`fabric-lifecycle-events-v1`、`fabric-resource-loader-v0` | `fabric.mod.json` |

## 2. 未验证的关键问题（M0 全部要给结论）

| # | 问题 | 为什么是生死线 | 验证方法 | 不通过的退路 |
|---|---|---|---|---|
| **Q1** | **专用服务端（dedicated server）是否可用？** 玩家装客户端、服务端也装同一套，能否正常起服、跑对局 | 我们是服务端玩法模组；Sable 若只能单机/局域网直连，整个方案作废 | 起 `runServer` + `runClient` 连接，造一个 sub-level 并移动 | 退路 A：改用 Eureka/VS2 + 1.20.1；退路 B：回到自研离散移动（已证不平滑，只能接受） |
| **Q2** | **玩家站在移动的 sub-level 上是否平滑随动？**（这正是我们缺的东西） | 移动手感是本次重做的起因 | 真人上筏 + `sail` 连续移动，视频/主观判定；同时看是否有 `moved wrongly` 刷屏 | 退路：限制筏速/改为"停靠式"玩法（筏不能边打边走），玩法要为此调整 |
| **Q3** | **筏上容器/熔炉/我们的设施方块实体在移动中是否可交互、数据是否保留？** | 原方案的"生产链 + 筏心 + 炮塔"全依赖这一点 | 放箱子/我们的设施 → 移动 100 格 → 开容器、核对 NBT | 退路：设施改为实体承载（改变玩法结构） |
| **Q4** | **建造（放置/破坏方块）能否作用在 sub-level 上？** | "不断收集物资强化木筏"是核心循环 | 在移动中的筏上放置与破坏方块，核对是否落到 sub-level 且随筏移动 | 退路：改为"靠岸建造 → 起航"的两段式（体验受损但可玩） |
| **Q5** | **性能：多筏 + 物理 + 12–18 人**的 TPS 与内存 | 长期服硬指标 | 4–6 个 sub-level 同时运动，压测 TPS/MSPT/内存增长 | 退路：限制筏体尺寸/数量，或改小局规格 |
| **Q6** | **与我们自己模组的共存**：Sable 的 mixin 会不会破坏我们的判定（伤害、方块交互、网络包、玩家移动） | F2 明说兼容性差 | 逐步接入我们的内容注册/命令/回合逻辑，回归测试 | 退路：把冲突面隔离到独立模块，或换依赖 |
| **Q7** | **API 可用性**：能否用代码创建/控制 sub-level（大小、位置、朝向、速度、上下客） | 决定我们写调用层的可行性与工作量 | ~~纯文档推测~~ **已解包确认 API 包存在（F10–F12）**；剩余问题是**调用方式与参数语义**：读 Developer Wiki + 反编译具体类，写最小 demo 跑通 | 退路：只能用它的"玩家手动造船"玩法 → 我们的玩法要重定义 |
| **Q8** | **竞技公平**：物理驱动的位置是否可被客户端利用（穿帮、卡进、加速） | 竞技服口碑底线 | 用修改包/异常包重放测试，看服务端是否权威 | 退路：关键判定（伤害、圈内外、淘汰）全部服务端重算 |
| **Q9** | **存档与重启一致性**：服务端崩溃/重启后 sub-level 状态是否完整恢复 | 长期服必然遇到 | 移动中 `kill -9`，重启核对筏体位置与 BE 数据 | 退路：局前状态由我们额外持久化一份（可能做不到等价） |
| **Q10** | **版本锁死风险**：Sable 只支持 1.21.1，若上游停更或改 API | 我们把它当核心依赖 | 检查仓库活跃度、issue 响应、许可证对 fork 的限制 | 退路：fork 冻结版本（Shield 允许修改但不得竞争性分发，需评估） |

## 3. 其它风险（非 Sable）

| ID | 风险 | 对策 |
|---|---|---|
| R1 | **玩法定义漂移**：一旦筏体行为由 Sable 决定，原方案里"划桨位移/筏心破拆/沉筏倒计时"可能要改 | 内容文档保留，但**每条玩法都标注"依赖 Sable 能力等级"**：A=直接可做 / B=需变通 / C=做不了要改玩法 |
| R2 | **拖局**（最后存活制固有） | 终局圈内持续掉血，而非加快缩圈 |
| R3 | **状态机制红线**：营养/水分/受伤不得单独致死 | 数值守住 + 回归用例 |
| R4 | **配置错误崩服** | 沿用旧计划的校验+拒绝加载+归档策略（`docs/content/03`） |
| R5 | **依赖链合规**：LGPL/MPL/Apache/PolyForm 混在一起 | `04-依赖与运维.md` 里逐条写清义务与打包方式 |
| R6 | **自动化并行开发冲突**（上一轮实际发生） | 自动化任务与人工会话**不得同时写同一仓库**；起服前先探端口；提交只按文件名 `git add` |

## 4. M0 验证清单（顺序即优先级，任一条失败就停下来汇报）

```
M0-1  依赖装配：Sable + 4 个前置模组 + Fabric 1.21.1 起服成功，不崩
M0-2  Q1 服务端可用性：runServer + runClient 能建 sub-level 并移动
M0-3  Q7 API：拿到"代码创建/移动 sub-level"的最小可用调用路径（含类名与方法名）
M0-4  Q2 手感：真人站上筏，连续移动 —— 平滑 / 可接受 / 不可接受（三选一，附视频）
M0-5  Q3 交互与保真：移动 100 格后容器可开、NBT 正确、设施数据在
M0-6  Q4 建造：在移动中的筏上放置与破坏方块是否正确生效
M0-7  Q5 性能：4 筏 + 物理 + 假人压测 TPS/内存
M0-8  Q6 共存：接入我们的注册表/命令/回合逻辑后回归无异常
M0-9  Q9 崩溃恢复：移动中强杀进程，重启后状态一致
M0-10 Q8 公平：异常客户端包重放，服务端仍权威
```

**M0 只做这件事，不写玩法功能代码。** 预计 5–9 人日（比旧计划低，因为不用自研引擎，但要读文档 + 试错）。

**Gate G0**：M0-1～M0-6 全绿才进 M1；M0-4（手感）由**你**判定，不接受我自己说"应该行"。

## 5. 失败时的决策树

```
M0-2 服务端不可用 ──→ 换 1.20.1 + Eureka/VS2（Apache/LGPL，许可更干净）
M0-3 API 不可用（只能手动造船）──→ 玩法重定义为"玩家自己造真船"，或退回自研离散移动
M0-4 手感仍不可接受 ──→ 木筏改为"停泊式"（建造/作战在停泊态，航行是过场），重新设计对局节奏
M0-5/6 交互或建造不成立 ──→ 生产链搬离筏体（岸上/浮岛设施），玩法结构改动，需你重新批
M0-8 与我们的代码冲突严重 ──→ 缩小我们的 mixin 面，或把冲突逻辑改为事件驱动
```
