### 实现口径的两次纠正（都是实测逼出来的）

1. **裸常数加速度不成立。** `applyLinearImpulse` 的注释写 `[N]`，它是**力**不是冲量
   （`RigidBodyHandle.java:115-121`）。`mass×0.05` 不到重力的 1%，筏子不动；
   `mass×30` 把筏**压穿池底石头掉到 Y=51**。
   → 改为"有效重量倍数"，重力取 `DimensionPhysicsData.getGravity(world,pos,dest)`（:57-62），
   换维度自动正确。倍数上限 **4.0**（6.0 实测穿地）。
2. **"触底即停压"是错的。** 停压 6 秒后浮力把筏子从 94.5 顶回水面 104.1——
   沉到一半又浮回去比不沉更糟。SUNK 是本局终态，所以**持续施加**，
   触底只记一次日志。穿模风险改由倍数上限拦。

另：Sable **没有任何质量写入口**（`MassTracker` 只有 getter、`RigidBodyHandle` 只有冲量/速度/传送、
全仓 `setMass|gravityScale|massMultiplier` 零命中），所以"加大重量"只能用等效力实现。

## 2. 筏心摧毁与残骸修复（01 §4.3.2 A2 + A2-v2）—— 通过

`tools/core_probe.py` **17/17**，分两局跑（SUNK 不可逆、每局额度只有 1 次，同局连测会互相吃掉前提）。

| 断言 | 实测 |
|---|---|
| 摧毁筏心 → 倒计时开始 | 队0 `COUNTDOWN` ✓（A2 第二条路径成立） |
| 按住 80 tick | 进度到 60/160，筏心仍是残骸 |

| **一边引导一边受伤** | 进度峰值只到 **11/160**，反复归零，始终修不好；且**不消耗额度** |
| 连续引导 160 tick | 筏心 `INTACT`、倒计时变 **IDLE（解除，不是重置）**、额度 1/1 |
| 额度用完再摧毁 | 命令明确回"本局修复额度已用完（1 次）"，不静默失败 |

判定全部下沉成零 MC 纯函数 `domain/raft/ChannelRule`（15 个单测，含"两人交替引导永远凑不满"
这条反绕过后门）。真机用 `/cww raftcore hold` 驱动：它只替换"客户端长按"这个输入源，
服务端推进/打断/额度/解除走的是与客户端接入后**完全相同**的一条路径。

### 我自己写错的两处

1. `hold` 最初在命令里自己循环调 `step()`：既与正常 tick 循环**重复推进**，
   又会在 RCON 线程里 sleep **卡住整个服务端**。改成只登记"模拟到第 N tick"。
2. 探针第一版把假玩家打死了（4×11 伤害 > 20 血），之后"找不到在线玩家"造成 4 条**假失败**；
   而且该局倒计时已走完到 SUNK，"恢复解除倒计时"在那一局里永远测不出来。伤害降到 1.0 并拆成两局。

## 3. 回合状态落盘与重启恢复（Gate G1 最后一条）—— 通过

`tools/restart_probe.py` **before 3/3 + after 7/7**。

```
重启前  phase=PLAY match=1 tickInPhase=1  arena=flat_test format=test_3min  参战 4 人
启动日志 [state] 已恢复到阶段 PLAY（match=1，阶段内 3 tick，参战 4 人）
重启后  phase=PLAY match=1 tickInPhase=50 arena=flat_test format=test_3min
        T0 赤队 [k0, k1]   T1 蓝队 [K2, k3]        审计尾部 3 条完整
```

新增 `domain/round/RoundSnapshot`（纯数据 + `validate()`）与 `round/RoundStateStore`
（原子写 tmp+ATOMIC_MOVE、`ABSENT/OK/INVALID` 三态、字段级错误）。每次阶段转移自动落盘，
另有 `/cww save` 与 `/cww statefile`。

### 这一条里踩到的三个真错

1. **快照必须记 arena/format 身份。** 第一版没记，重启时加载的是默认 format（4×3），
   快照是 2×2，`restore()` 的规格校验**正确地拒绝恢复**——看起来是守卫的锅，
   实际是快照缺了"这一局用的是哪套配置"。加上 `arenaId/formatId` 并把 `loadConfigs`
   提到 `restore` 之前才成立。
2. **队伍骨架必须构造时就建。** `ensureTeams()` 原本是懒的，新机器快照里 `teams` 为空，
   于是同一个校验又把正常快照判成非法。改成构造时调用（它本来就幂等），
   顺带让 `/cww state` 在 LOBBY 就能看到队伍而不是 `teams=0`。
3. **测试机也要设身份。** `formatId` 为空时存储层拒绝恢复是对的，
   但我的测试没模拟 `loadConfigs` 的那一步，暴露的是测试不完整而不是产品 bug。

### 落盘层的三条硬要求（写进代码注释）

- 原子写：长期服随时可能被 kill，半截 JSON 比没有 JSON 糟糕得多。
- "文件不存在"与"文件读坏了"必须分开处理：前者是正常首次启动，后者必须 ERROR 并留在 LOBBY，
  **绝不"尽力恢复"**。
- 写入型数据只进 `<world>/cww/state/`，绝不碰 `arenas/` 与 `formats/`（03 §5 的分离要求）。

| 断言 | 实测 |
|---|---|
| 尺寸来自配置 | `limits.initialRaftRadius=3` → 49 格甲板 → 质量 **24.5**（49×0.5，`#sable:light`） |
| 落点 | 两队都在出生锚点，Y=149.50（flat_test 水面 149） |
| 命名 | `nbw_raft_<队>`，`/sable info @e` 直接可查 |

| 玩家落位 | 4 个假玩家 Y 都在 149（在筏面上，不在水里） |
| **收局残留** | 筏全部销毁、票全部释放、`[S10] residue=CLEAN` |

设计取舍：
- **用 `allocateNewSubLevel` + 往 plot 铺方块，不用 `assembleBlocks`。** 装配要求世界上已有这些方块，
  而开局要的是"凭空造一艘形状可控、可复现的筏"；而且装配在水上还会踩连通域漏水的坑（T0）。
- **`initialRaftRadius` / `initialRaftBlock` 放进 arena 的 `limits`，不放 format。**
  筏子多大是"这张图"的空间事实，赛制只管时间与人数（03 §2 的字段归属）。两个字段都是可选的，
  缺省走 `DEFAULT_RADIUS=3`，所以旧的 arena 文件不会被这次改动打废。
- **先建锚点→再发筏→最后传人。** 顺序反了玩家会落进水里等筏子凭空出现。
- **`plot 网格已满` 翻译成可读失败而不是崩对局。** `allocateNewSubLevel` 满了抛
  `IllegalStateException`，16384 槽位对长期服是真实约束，不是假想。

回归确认：发筏接进 READY 之后，`m1_round.py` 2 局 + abort 路径 **58/58、0 异常日志**，
残留复检跨 3 局仍然 CLEAN；`sink_probe` 15/15、`core_probe` 17/17 也都没被影响
（core_probe 现在能看到队 1 也有绑定的筏，正是自动生成生效的迹象）。

## 3.6 筏心方块本体（M2-4 前半）—— 通过

`tools/raftgen_probe.py` **18/18**、`core_probe` **18/18**、`sink_probe` 15/15。

### 这轮回答了一个之前没人验证过的关键问题

**自定义方块实体在 Sable 的 sub-level plot 里到底会不会被 tick？**

答案是：**原版那条路走不通，Sable 留了专用通道。**
`ServerLevelPlot.tick()` 只跑光照与 contraption 清理，**完全不 tick 方块实体**。
每 tick 行为的唯一入口是实现 Sable 的 `BlockEntitySubLevelActor`——
`LevelPlot.java:410-416` 靠 `instanceof` 决定要不要收进 actor 表，
再由 `ServerSubLevel.java:299`（游戏 tick）与 `SubLevelPhysicsSystem.java:226`（物理 tick）调用。
所以 **BE 必须自己实现那个接口**，中间加适配器不会被注册。

实测证据：`[content] 筏心登记（BE 已被 Sable tick）` 出现 2 次（每队一条）。

### 因此记下一条架构例外

"全工程只有 `sable/` 允许 import Sable"这条纪律，现在有一处**刻意的例外**：
`content/RaftCoreBlockEntity` 实现 `BlockEntitySubLevelActor`。
例外只到"实现接口"为止——接口方法内部要调的 Sable 能力仍然走 `sable/`。
这是接口约束不是设计偷懒，写进代码注释而不是藏着。

### 质量算式顺手成了方块真进 plot 的证据

初始筏质量从 **24.5 变成 25.5** = 49 格木板×0.5 + 筏心 1.0（完整方块默认质量）。
筏心是用 `plot.getEmbeddedLevelAccessor().setBlockState()` 写在 **plot 局部坐标 (0,1,0)** 的，
原版 `setBlockState` 负责创建方块实体。

### 一个差点埋进产品的坐标陷阱

BE 在自己 tick 里看到的 `getPos()` 是 **plot 局部坐标**（实测 `x=20481032` 这种量级），
而交互回调给的 pos 属于哪个坐标空间**没有保证**。两套空间一旦错位，
表现是"玩家怎么点都没反应"，而且日志里什么都不会报。
所以 `onUse` 改成**从玩家实际点到的那个 BE 读归属**，不再按坐标查表。

### 两个我主动没写的东西

1. **`onBroken` 没写。** 1.21.1 的 Yarn 里它有两个归属不明的重载
   （`(DamageSource, World, BlockPos)` 与 `(WorldAccess, BlockPos, BlockState)`），
   而"武器打掉筏心"本来要等 M4 的武器表。破坏只留一个入口 `RaftCoreService.markDestroyed`，
   方块状态由 `syncState` 每 tick 回写。与其猜个签名把逻辑钉死在错的钩子上，不如等伤害来源出现再挂。
2. **`onUseWithItem` 没写。** 1.21.1 把右键拆成空手 `onUse(state,world,pos,player,hitResult)`
   与拿东西 `onUseWithItem(stack,...)`。带物品那一半和客户端长按周期包是同一个问题的两面
   （玩家真在修的时候手里往往有工具），分开写会各测一半，所以一起等客户端包时补。

### 新增的可断言证据

`/cww raftcore status` 现在带 `状态回写 N 次`。没有它，"倒计时在走但方块看着还是好的"
这种不一致在日志里完全看不出来，玩家也无从判断该不该去修。

## 3.7 帆与航行的第一手数据（M2 航行入口）

`tools/sail_probe.py` **8/8 + 1 条主动标为 INCONCLUSIVE**。这一节里有两条对玩法影响最大的读数，
以及一条我**拒绝假装通过**的断言。

### 结论一：帆在 Sable 的默认物理下不能推进（已证实）

Sable 默认维度物理 `basePressure = 1.0`，但压力是**只随 Y 变化的标量**
（`DimensionPhysics.createDefault` 用 `exp(-0.004·(y-seaLevel))` 拟合贝塞尔），
**没有风向矢量**。静风时帆相对空气的速度就是筏自己的速度，升力项推不出前进方向。

实测：静止状态下挂 5 块帆，6 秒内速率峰值 **0.011**（阈值 0.25）。
→ **帆是阻力面 / 龙骨，不是发动机。** 推进只能靠桨/螺旋桨（要客户端输入）
或我们自己往 dimension physics 里加风场。这条直接约束 P-01 的数值范式。

### 结论二：无动力时筏子只能滑 2 秒（已证实，影响最深）

同一冲量下的速率曲线：`0.332 → 0.047 → 0.007 → 0`，**约 2 秒就完全停住**。
→ 持续动力不是"可选优化"，是硬需求。12 分钟的局里要横跨几百格海域，
靠一次性冲量完全不可行。这条比帆的结论更该影响 M2 的排期顺序。

### 结论三：帆的阻力增量<b>没测出来</b>（我拒绝让它假绿）

第一版断言写成"带帆减速所需秒数 ≤ 无帆秒数"，结果两边都是 2 秒，**平凡通过**。
而挂帆后质量从 25.5 变 30.5，同一冲量下初速必然更低，直接比绝对值会把质量差异误读成阻力差异。
改成归一化比值后：无帆 `0.021`、有帆 `0.019`，差 0.02，落在噪声里。
→ 探针现在明确打印 `INCONCLUSIVE` 而不是 OK。**5 块帆的阻力作用在这个尺度上无法与噪声区分，
不据此下结论**；要判定就得加大帆面积或换更长的测量窗口。

### 顺带修掉两个会进生产的真 bug

1. **扫 `plot.getBoundingBox()` 把服务端冻住 5.2 秒**（日志 `Can't keep up! ... 103 ticks behind`）。
   原因：plot 局部坐标不是直觉里的 `-3..3`，而是相对 plot 网格槽位的大数
   （筏心 BE 的 `getPos()` 实测 `x=20481032`），包围盒跨度到几百万格，三重循环就是灾难。
   → 改成自己登记帆的局部偏移，数与拆只遍历这张小表。
   后果不止是卡顿：那次冻结让 RCON `stop` 失效、进程占死 25565/25576，下一个服务端起不来。
2. **恢复进 PLAY 后筏子绑定丢失**。sub-level 本身跨重启存活，但 `spawned`（队→筏 UUID）
   是运行时状态、没进快照，于是恢复的那一局"筏子在眼前漂着，而沉筏/挂帆/清理全找不到它"，
   命令只会回一句"队 0 没有筏"。→ 新增 `rebindFromWorld()`，按命名约定 `nbw_raft_<队>` 反查重认领。

另外还修了一条：打完一局的 LOBBY 快照里 `teams` 是空的，
而 `restore()` 的规格校验把"0 支队伍"当成非法快照拒绝——等于每打完一局重启都恢复失败。
空表现在按当前规格重建。

### 一个场地事实

`flat_test` 只是 y=148 的旱地基岩平台，**没有水**。筏子搁在上面不是船，
所以航行类测试必须先造海（探针里已加）。这也说明 M2 之后需要一个真带水的 arena，
对应 M3 的黑海，不能一直借 drill 的旱地平台测航行。

## 3.8 风推进（M2-5）—— 通过，并留下一条未结案

`tools/wind_probe.py` **11/11**、`WindModelTest` **11 个单测**（全量 129 个）。

### 风解决了上一轮那条硬结论

`cww wind set north 2.0` + 5 块朝北的帆，12 秒速率曲线：
```
2.768, 3.060, 0.475, 0.271, 0.270, 0.303, 0.292, 0.289, 0.290, 0.292, 0.291, 0.290
```
→ 末 4 秒稳定在 **0.29 m/s（≈5.8 格/秒）不掉回 0**。对比无动力时"2 秒完全停住"，
风确实提供了**持续动力**，不是又一次冲量。前两点 2.7/3.0 是上一次操作留下的残余运动，不是风的效果。

> **⚠ 2026-11-05 连续三次更正，最终版（前面两条都是我的错）：**
>
> 1. **本节最初的说法（"Sable 不采样外层世界的水、0.29 是水上终端速度"）不成立。**
>    读 `sable_rapier/.../rapier/src/buoyancy.rs` 后确认：`do_float` 逐格读**父世界**方块
>    （`chunk.get_block(...)` → `voxel_collider_data.volume`）给出 `10.5·体积` 的浮力，
>    `do_drag` 给出 `-速度·1.7·浸没体积` 的**水阻**。筏子能漂在水面、沉下去能落到底，靠的就是它。
>    → 所以"造海不改变航行读数"这句也是错的，它当时被我用来推导缺陷 B 的性质。
> 2. **我上一轮写的"真海上一路加速到 3.0~3.8 格/tick"是测量污染**：采样前我自己注入了
>    `sable physics impulse … 60`，那条曲线是**冲量余波的衰减**，不是风推的加速度。
>    重测纯滑行（不注冲量、只给初速）：**2.13 → 0.88 → 0.37 → 0.15 → 0.06 → 0.03 → 0**，
>    τ ≈ 0.27 秒归零 —— **水阻不但存在，而且很强**。
> 3. 帆数对滑行衰减几乎无影响（0/5/7 帆三条曲线重合，比值都是每 0.25s 约 ×0.41）
>    → **帆不额外产生水阻**（帆在水线以上，浸没体积不变）。所以"帆多更快"要的是
>    推力随帆数增长，这一项我们本来就有；缺陷 B 不是"缺阻力模型"。
> 4. **终端速度目前仍未量出来**：`wind north 2.0` 下 0 帆、1 帆都读回 `0.0000`，
>    5/7 帆在冲量余波消退后停在 ~0.11。而且 `test_sea` 半径只有 60、锚点在 0.8R=48，
>    筏子几秒就撞到海域边缘被卡住 —— **这块场地测不了航行终端速度**。
>    测法要求：`default_sea` 上取一条长直航段、每档复位到锚点、绝不注入冲量、对局没结束前测完。
> 5. **修好测法后的第一组可信读数（0 帆作对照、绝不注入冲量）**：
>    `3 帆 → 合力 6.0 → 1.546 格/tick ≈ 30.9 格/秒`；`0 帆 → 合力 0、速度 0.0000`（对照组过）。
>    **方向和"风推不过水阻"正好相反：现在的疑问是推力太强。** 31 格/秒意味着
>    半径 60 的 `test_sea` 撑不满 4 秒，半径 140 的 `default_sea` 也只能跑约 9 秒就到岸 ——
>    所以 5 帆、7 帆读回的 0 **是撞边卡住 + 对局超时把筏清场**（同一次 `step 9` 也因此在
>    `No sub-levels found` 上失败），不是物理结论。探针已相应改成"每档复位到锚点 + 对局掉了就重开"。
>    在这条被 `default_sea` 上的长直航复测推翻之前，**证据是反对去改 Sable 阻力代码的**：
>    水阻已经在（∝浸没体积×速度），要动的更像是我们自己的推力口径。

### 另外三条同时被证实

| 断言 | 实测 |
|---|---|
| 无风时帆不产生任何力（对照组） | 峰值 0.011 |
| **背风不产生反向力** | 朝北的帆遇南风，峰值 **0.001**（帆不会变成"倒车挡"） |
| 无帆的筏不受风力 | 队 1 全程 0.000（帆是受风面，裸筏只能靠桨） |
| 公平性：全局单值 | 两队读到完全相同的风 `('0.000','-1.000','3.00')` |

### 为什么风在我们这侧而不是 Sable 里

Sable 的翼型公式只用"相对空气的速度"，而它的维度物理只有 `basePressure`（随 Y 衰减的标量）
与 `gravity`，**没有任何风向矢量**。要让它有风就得改那段翼型计算，也就是 fork。
本项目原先的"Sable 只读不改"纪律已由用户于 2026-11-05 放开：**功能要确定与 Sable 关联来实现，
必要时直接调整 Sable 源码**，不要再在旁边另起一套平行自研。风放在我们这侧仍然是对的
（Sable 确实没有风向矢量），但下一条 #32（终端速度/水阻）要先去扫 Sable 自带的
`universalDrag` 与 `floating_materials` 摩擦系数，而不是先写我们自己的阻力公式。
附带好处：事件池里的风暴/顺风可以直接调 `WindService.set`，圈层风场差异以后也能加。

`SableRafts.push` 与 `sink` 的区别是刻意的：`sink` 是"变重"所以按质量成比例，
风是**真实外力**不乘质量——乘了会让风对大筏不公平地更强。

### `core_probe` 的夹具缺陷：已结案（19/19）

排查过程（每一步都推翻了上一步的结论）：
1. 先怀疑产品 → 不是：进度直方图显示活着时能推到 40/80/83。
2. 再怀疑伤害打死引导者 → 部分对：`damage 1.0 × 11` 确实把 c0 打死，死玩家不能引导是正确行为。
3. 降到 0.5 伤害并在第 4 步前 kill+spawn 复位 → **仍然失败**，进度卡在 19/160 每秒重来。
4. 真因：`player <名> kill` + `spawn` 会让 **Carpet 假玩家换 UUID**，
   而模拟引导绑的是旧 UUID，`getPlayer(旧UUID)` 永远返回 null → 每 tick 重新武装、约 20 tick 打断一次。

真实玩家重生**不换 UUID**，所以这不构成产品缺陷。但它暴露一条必须写下来的约束：
**引导绑的是玩家身份（UUID），实体被替换时引导该不该继续，是一个要有明确答案的设计问题**——
现在的行为是"绑不到就打断"，对真人是合理的（死了就该断），
但以后加"复活后继续引导"之类的需求时，不能想当然。

`core_probe` 的修复方式很清楚（每局用全新名字起假玩家，不复用被 kill 过的名字），
留到下一轮做，**这一轮不声称它通过**。

### 取证到的三条事实（都改了设计）

1. **筏子的浮力与水阻来自 Sable 逐格读父世界方块（我先前这条搞错了，见 §3.8 最终版更正）。**
   Sable 有两条路径：Java 侧 `FloatingBlockController`（按 `floating_materials` 材质查表，
   不读世界流体）+ **Rust 侧 `buoyancy.rs`**：`do_float` 用 `chunk.get_block(...)` 拿方块体积给
   `10.5·体积` 浮力，`do_drag` 给 `-速度·1.7·浸没体积` 水阻。实测纯滑行 τ≈0.27 秒归零，
   说明后一条对我们生效且**阻力很强**。→ 造海会改变航行读数；缺陷 B 不是"缺阻力模型"，
   而是"推力与水阻的比例没配过、且我们从没在能跑的场地上量过终端速度"。
2. **持票的 sub-level 不会被踢出物理管线。** `PhysicsChunkTicketManager:167` 对
   `collectForceLoadedSubLevels()` 里的 sub-level 走 `inhabitChunk` 分支，由 Sable 自己给外层区块下票；
   只有**没票**的才会走 `:183 moveToUnloaded`。我们的筏已经持 `nbw:round_active`，
   所以原计划的第二张 `nbw:arena_active` 票**取消**（会是恒真断言）。
   真机验证：把筏传到没有任何 forceload 的 (-1000,700)，14 秒后姿态仍读得到 `Y=63.05`。
3. **1.21.1 datapack 约定已核实**：目录是单数 `data/<ns>/function/`（FunctionLoader 常量池含
   `"function"`/`".mcfunction"`）；函数宏可用；`return` **只接受裸 `return fail`**，
   写 `return fail 0` 会让整个函数**静默加载失败**；mod jar 里的 `data/` 会被自动挂载（Sable 自己就这么发）。

**做法**：`WindModel.FORCE_PER_SAIL` 1.0 → **0.2**（真机标定），新增 `MAX_SAIL_SPEED = 0.45` 格/tick

|---|---|---|---|
| 0 | 0.00 | 0.000 | 对照组：无帆不受风 ✓ |
| 1 | 0.40 | **0.156** 格/tick | 3.1 格/秒 |

`RoundMachine` 判 `aliveTeamCount()==1` 提前结算、筏子被清场，于是第 2 档之后所有读数都是 0——
看着像"风推不动"，其实是"场上没有筏子"。修法全在夹具侧：假玩家加 `water_breathing`；

**教训：测航行的对局必须能活过整轮扫描。**

**没改 Sable**：水阻本来就在（`∝浸没体积×速度`），问题出在我们自己的推力口径，
按"完全确定和 Sable 关联来实现"的原则这次不需要动依赖。残留的加载开销另记 #35。

1. `data get storage <store> rows` 在队列有 525 条时回包过大，**服务端直接掐断 RCON 连接**
   → 改成 `execute if data … rows[0] run data get … rows[0]` 只取队首。
2. `tools/rcon.py:_recv` 在连接被关闭时是**死循环**而不是报错，于是"掐线"表现为"探针无声卡住"；

3. 同一连接上连着发"命令 + 哨兵"会被服务端掐线；单发 + `select` 只读已到达的包才稳。

### 本轮查出来的两个口径问题（都不是桨本身的错，但都会骗人）

1. **读数不等于位移，差约 22 倍。** 满员划桨 8.1 秒实际只走 **2.4 格（0.29 格/秒）**，
   而同一时刻的速率读数是 0.3207 格/tick（6.41 格/秒）。对照实验：给一个已知的
   `sable physics impulse 12` 之后，读数还有 0.0169，筏子实际只挪了 0.23 格。
   根因是我们每 tick 用 `applyLinearImpulse` 施力，读到的是施力后的**瞬时峰值**，
   而 Sable 的水阻在同一 tick 内就把绝大部分速度吃掉。
   影响面：`WindModel.MAX_SAIL_SPEED`、P-01 的"≈2/3/5/8 格/秒"、以及我写在注释里的
   "横穿 280 格约 31 秒"——**这些都按读数算过，必须用位移重标**（任务 #39）。
   探针已加了一条位移实测与"读数/位移"倍数的打印，这个偏差以后藏不住。
2. **同名 sub-level 残骸会让位置读数骗人。** 一次性配对实验里
   `sable storage find_all_sub_levels` 列出 **3 只 nbw_raft_0 + 3 只 nbw_raft_1**
   （多轮开局/重启/崩溃遗留）。按名字取位置与按 UUID 取速度会配到不同个体，
   表现正是"速率 0.1078 而漂行 0 格"。清理之后（1 只）同一读数下位移是 2.4 格，
   说明残骸确实是位置类读数的干扰源。`sable remove` 报 "Removed 3 sub-levels" 后
   `find_all_sub_levels` 仍列出旧条目，但**下次关档之后确实消失了** —— 删除是在存档时落盘的，
   我原本写成"不清盘"是过头的结论，已在任务 #38 更正。
   探针因此加了"盘上同名筏体数量"的打印，并在 >1 时把漂行标注为只作参考。

### 重启恢复：第一次"通过"是假象，清干净世界才看到真问题

第一轮跑 `oar_restart_probe.py` 时 after 段报"桨=2 自己回来了"，我据此差点写下"重启不用重新挂桨"。
把 dev 世界的同名残骸清掉之后（`sable storage find_all_sub_levels` 从 3+3 只降到 1 只）再跑，
同一套断言直接掉回 桨=0、"本局还没生成过筏"。**先前那条结论是被同号残骸撑出来的假绿。**

真问题在恢复时序上，日志顺序是决定性证据：

```
12:20:57  [raftgen] 重启重认领 0 艘筏；没找到：队 0 队 1
12:20:57  [state] 已恢复到阶段 PLAY（match=62，阶段内 130 tick，参战 2 人）
12:20:59  [oar] 桨位回填 team=0 slot=0 ...        ← sub-level 两秒后才载进来
```

`rebindFromWorld` 只在恢复那一刻调用一次，而那一次 Sable 还没把 sub-level 装进容器，
于是"恢复出来的这一局看不见自己的筏"：桨力、挂帆、沉筏、局后清理全都指向不到实体。
修复是把认领变成**可延后重试**：`RoundManager` 的 tick 里，对局进行中每 20 tick 检查一次
`RaftSpawner.needsRebind()`，还有队没绑上就重试（`rebindFromWorld` 本来就幂等：补 UUID + 绑沉筏 + 补票），
并把"这队没找到筏"的话术按队去重，避免每 20 tick 刷一行同样的缺失清单。

修复后实测（after 段 11/11）：

| 断言 | 结果 |
|---|---|
| 全程不调用 `oar rig`，`oar read` 仍是 桨=2 | 通过（身份来自 BE 的 NBT） |
| 回填的方向与 plot 偏移原样回来 | 通过：`dir=(0, 1)`、`(-3,1,-2)`/`(-3,1,-1)` |
| 重启后这队的筏被重新认领 | 通过：`队0 Y=63.84 质量=27.5`（比空筏 25.5 多出的正是 2 台桨） |
| 按回填偏移真能拆掉桨 | 通过：`拆掉 2 台桨台`，第二次拆报 0 台 |
| 划桨状态不跨重启 | 通过：在划=0（否则就是凭空多出动力） |
| 同号重复筏体必须吵出来 | 通过：6 行回填、4 次重复认领 → 2 行 ERROR（#38） |

**仍然没验的一条**："重启后仍然划得动"。对局进行中既不允许中途加入也不允许改队，
而 Carpet 假玩家重启后不是同一个 UUID，探针拿不到一个"已分配的划桨者"——这条留在 §6 的真人清单里。

## 4. Q9 · Sable sub-level 跨重启（顺带拿到数据）

造一艘筏、推开、上加载票、重启：

| 项 | 重启前 | 重启后 |
|---|---|---|
| 位置 | 400.0 **104.155** 400.715 | 400.0 **103.976** 400.715 |
| 质量 | 24.5 | 24.5 |
| 速度 | (0, −0.064, 0.008) | (0, 0, 0)（重新沉降稳定） |
| 加载票 | `sable:command_forced` | **仍然存在** |
| 是否自动载入内存 | — | 是（`/sable info @e` 直接能找到） |

两条结论：
1. sub-level 的位置与形态跨重启**保真**，`storage find` 也能按名字查到。
2. **加载票会跨重启存活** —— 这是运维隐患：我们的 `nbw:round_active` 票如果结算时漏收，
   筏子会被永久钉在内存里，重启也不会释放。收票必须做成局后清理的**断言项**而不是"记得做"。

（早先担心的 `sub_level_velocity_retained_on_load=0.9` 会让筏子重启后"窜一下"，
实测影响很小：保留的是保存瞬间的速度，而沉底/静止时那个速度本就接近 0。）

### 长按输入通道（M2-4 欠的那一半，本轮接上）

真人长按右键终于能喂进 A2-v2 的引导判定：`net/HoldPayload`（C2S，只有目标坐标 + active 标志）、
`net/NbwNetworking`（服务端 codec + 接收器）、`client/HoldInputClient`（按住每 2 tick 续包，松手补一刀），
判定口径放在 `domain/net/HoldPolicy`（6 条单测）。服务端侧起服验证通过：
`[net] 长按输入通道已注册：nbw:hold（可达上限 8.0 格，窗口 4 tick）`，专用服务端没有因客户端类而崩。

**这一版 API 的考古结论，别再来一遍：**

| 事实 | 依据 |
|---|---|
| yarn 1.21.1 **没有** `PayloadTypeRegistry` / `playC2S` 在 MC 侧；注册表在 **fabric 自己包里**：`net.fabricmc.fabric.api.networking.v1.PayloadTypeRegistry.playC2S().register(Id, PacketCodec)` | fabric-networking-api-v1 4.3.1 javap |
| **codec 注册与接收器注册是两件事**，只注册接收器则服务端解不出包 | 同上 javap 签名 |
| `ServerPlayNetworking.registerGlobalReceiver(CustomPayload.Id<T>, handler)`；`Context` 只有 `server()/player()/responseSender()` | javap |
| `PacketCodec.of` 的编码器是 **`ValueFirstEncoder`：值在前、buf 在后**，与 Mojang `StreamCodec` 参数顺序相反 | 编译报错 "无法将方法 of 应用到给定类型" 后查 `za → ValueFirstEncoder` |
| 内联 lambda 写在 record 的静态字段初始化里会让 javac 推断错参数（报 `找不到符号 p.pos()`），用具名静态方法即可 | 实测 |
| 服务端类里不许出现 `MinecraftClient` 等客户端类，否则专用服务端 `NoClassDefFoundError`；故拆 `client/HoldInputClient` | 结构约定 |

**仍未验证的部分**：包真的从客户端到服务端这一段（假玩家发不出自定义包），要真人客户端试——见 §6。
