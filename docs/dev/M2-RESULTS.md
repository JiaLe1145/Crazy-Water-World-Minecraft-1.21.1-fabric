### 实现口径的两次纠正（都是实测逼出来的）

1. **裸常数加速度不成立。** `applyLinearImpulse` 的注释写 `[N]`，它是**力**不是冲量
   （`RigidBodyHandle.java:115-121`）。`mass×0.05` 不到重力的 1%，筏子不动；
   `mass×30` 把筏**压穿池底石头掉到 Y=51**。
   → 改为"有效重量倍数"，重力取 `DimensionPhysicsData.getGravity(world,pos,dest)`（:57-62），
   换维度自动正确。倍数上限 **4.0**（6.0 实测穿地）。
2. **"触底即停压"是错的。** 停压 6 秒后浮力把筏子从 94.5 顶回水面 104.1——
   沉到一半又浮回去比不沉更糟。SUNK 是本局终态，所以**持续施加**，
   触底只记一次日志。穿模风险改由倍数上限拦。

另：Sable **没有任何质量写入口**（`MassTracker` 只有 getter、`RigidBodyHandle` 只有冲量/速度/传送、
全仓 `setMass|gravityScale|massMultiplier` 零命中），所以"加大重量"只能用等效力实现。

## 2. 筏心摧毁与残骸修复（01 §4.3.2 A2 + A2-v2）—— 通过

`tools/core_probe.py` **17/17**，分两局跑（SUNK 不可逆、每局额度只有 1 次，同局连测会互相吃掉前提）。

| 断言 | 实测 |
|---|---|
| 摧毁筏心 → 倒计时开始 | 队0 `COUNTDOWN` ✓（A2 第二条路径成立） |
| 按住 80 tick | 进度到 60/160，筏心仍是残骸 |

| 连续引导 160 tick | 筏心 `INTACT`、倒计时变 **IDLE（解除，不是重置）**、额度 1/1 |
| 额度用完再摧毁 | 命令明确回"本局修复额度已用完（1 次）"，不静默失败 |

判定全部下沉成零 MC 纯函数 `domain/raft/ChannelRule`（15 个单测，含"两人交替引导永远凑不满"
这条反绕过后门）。真机用 `/cww raftcore hold` 驱动：它只替换"客户端长按"这个输入源，
服务端推进/打断/额度/解除走的是与客户端接入后**完全相同**的一条路径。

### 我自己写错的两处

1. `hold` 最初在命令里自己循环调 `step()`：既与正常 tick 循环**重复推进**，
   又会在 RCON 线程里 sleep **卡住整个服务端**。改成只登记"模拟到第 N tick"。
2. 探针第一版把假玩家打死了（4×11 伤害 > 20 血），之后"找不到在线玩家"造成 4 条**假失败**；
   而且该局倒计时已走完到 SUNK，"恢复解除倒计时"在那一局里永远测不出来。伤害降到 1.0 并拆成两局。

## 3. 回合状态落盘与重启恢复（Gate G1 最后一条）—— 通过

`tools/restart_probe.py` **before 3/3 + after 7/7**。

```
重启前  phase=PLAY match=1 tickInPhase=1  arena=flat_test format=test_3min  参战 4 人
启动日志 [state] 已恢复到阶段 PLAY（match=1，阶段内 3 tick，参战 4 人）
重启后  phase=PLAY match=1 tickInPhase=50 arena=flat_test format=test_3min
        T0 赤队 [k0, k1]   T1 蓝队 [K2, k3]        审计尾部 3 条完整
```

新增 `domain/round/RoundSnapshot`（纯数据 + `validate()`）与 `round/RoundStateStore`
（原子写 tmp+ATOMIC_MOVE、`ABSENT/OK/INVALID` 三态、字段级错误）。每次阶段转移自动落盘，
另有 `/cww save` 与 `/cww statefile`。

### 这一条里踩到的三个真错

1. **快照必须记 arena/format 身份。** 第一版没记，重启时加载的是默认 format（4×3），
   快照是 2×2，`restore()` 的规格校验**正确地拒绝恢复**——看起来是守卫的锅，
   实际是快照缺了"这一局用的是哪套配置"。加上 `arenaId/formatId` 并把 `loadConfigs`
   提到 `restore` 之前才成立。
2. **队伍骨架必须构造时就建。** `ensureTeams()` 原本是懒的，新机器快照里 `teams` 为空，
   于是同一个校验又把正常快照判成非法。改成构造时调用（它本来就幂等），
   顺带让 `/cww state` 在 LOBBY 就能看到队伍而不是 `teams=0`。
3. **测试机也要设身份。** `formatId` 为空时存储层拒绝恢复是对的，
   但我的测试没模拟 `loadConfigs` 的那一步，暴露的是测试不完整而不是产品 bug。

### 落盘层的三条硬要求（写进代码注释）

- 原子写：长期服随时可能被 kill，半截 JSON 比没有 JSON 糟糕得多。
- "文件不存在"与"文件读坏了"必须分开处理：前者是正常首次启动，后者必须 ERROR 并留在 LOBBY，
  **绝不"尽力恢复"**。
- 写入型数据只进 `<world>/cww/state/`，绝不碰 `arenas/` 与 `formats/`（03 §5 的分离要求）。

| 断言 | 实测 |
|---|---|
| 尺寸来自配置 | `limits.initialRaftRadius=3` → 49 格甲板 → 质量 **24.5**（49×0.5，`#sable:light`） |
| 落点 | 两队都在出生锚点，Y=149.50（flat_test 水面 149） |

| **收局残留** | 筏全部销毁、票全部释放、`[S10] residue=CLEAN` |

设计取舍：
- **用 `allocateNewSubLevel` + 往 plot 铺方块，不用 `assembleBlocks`。** 装配要求世界上已有这些方块，
  而开局要的是"凭空造一艘形状可控、可复现的筏"；而且装配在水上还会踩连通域漏水的坑（T0）。
- **`initialRaftRadius` / `initialRaftBlock` 放进 arena 的 `limits`，不放 format。**
  筏子多大是"这张图"的空间事实，赛制只管时间与人数（03 §2 的字段归属）。两个字段都是可选的，
  缺省走 `DEFAULT_RADIUS=3`，所以旧的 arena 文件不会被这次改动打废。
- **先建锚点→再发筏→最后传人。** 顺序反了玩家会落进水里等筏子凭空出现。
- **`plot 网格已满` 翻译成可读失败而不是崩对局。** `allocateNewSubLevel` 满了抛
  `IllegalStateException`，16384 槽位对长期服是真实约束，不是假想。

回归确认：发筏接进 READY 之后，`m1_round.py` 2 局 + abort 路径 **58/58、0 异常日志**，
残留复检跨 3 局仍然 CLEAN；`sink_probe` 15/15、`core_probe` 17/17 也都没被影响
（core_probe 现在能看到队 1 也有绑定的筏，正是自动生成生效的迹象）。

## 3.6 筏心方块本体（M2-4 前半）—— 通过

`tools/raftgen_probe.py` **18/18**、`core_probe` **18/18**、`sink_probe` 15/15。

### 这轮回答了一个之前没人验证过的关键问题

**自定义方块实体在 Sable 的 sub-level plot 里到底会不会被 tick？**

答案是：**原版那条路走不通，Sable 留了专用通道。**
`ServerLevelPlot.tick()` 只跑光照与 contraption 清理，**完全不 tick 方块实体**。
每 tick 行为的唯一入口是实现 Sable 的 `BlockEntitySubLevelActor`——
`LevelPlot.java:410-416` 靠 `instanceof` 决定要不要收进 actor 表，
再由 `ServerSubLevel.java:299`（游戏 tick）与 `SubLevelPhysicsSystem.java:226`（物理 tick）调用。
所以 **BE 必须自己实现那个接口**，中间加适配器不会被注册。

实测证据：`[content] 筏心登记（BE 已被 Sable tick）` 出现 2 次（每队一条）。

### 因此记下一条架构例外

"全工程只有 `sable/` 允许 import Sable"这条纪律，现在有一处**刻意的例外**：
`content/RaftCoreBlockEntity` 实现 `BlockEntitySubLevelActor`。
例外只到"实现接口"为止——接口方法内部要调的 Sable 能力仍然走 `sable/`。
这是接口约束不是设计偷懒，写进代码注释而不是藏着。

### 质量算式顺手成了方块真进 plot 的证据

初始筏质量从 **24.5 变成 25.5** = 49 格木板×0.5 + 筏心 1.0（完整方块默认质量）。
筏心是用 `plot.getEmbeddedLevelAccessor().setBlockState()` 写在 **plot 局部坐标 (0,1,0)** 的，
原版 `setBlockState` 负责创建方块实体。

### 一个差点埋进产品的坐标陷阱

BE 在自己 tick 里看到的 `getPos()` 是 **plot 局部坐标**（实测 `x=20481032` 这种量级），
而交互回调给的 pos 属于哪个坐标空间**没有保证**。两套空间一旦错位，
表现是"玩家怎么点都没反应"，而且日志里什么都不会报。
所以 `onUse` 改成**从玩家实际点到的那个 BE 读归属**，不再按坐标查表。

### 两个我主动没写的东西

1. **`onBroken` 没写。** 1.21.1 的 Yarn 里它有两个归属不明的重载
   （`(DamageSource, World, BlockPos)` 与 `(WorldAccess, BlockPos, BlockState)`），
   而"武器打掉筏心"本来要等 M4 的武器表。破坏只留一个入口 `RaftCoreService.markDestroyed`，
   方块状态由 `syncState` 每 tick 回写。与其猜个签名把逻辑钉死在错的钩子上，不如等伤害来源出现再挂。
2. **`onUseWithItem` 没写。** 1.21.1 把右键拆成空手 `onUse(state,world,pos,player,hitResult)`
   与拿东西 `onUseWithItem(stack,...)`。带物品那一半和客户端长按周期包是同一个问题的两面
   （玩家真在修的时候手里往往有工具），分开写会各测一半，所以一起等客户端包时补。

### 新增的可断言证据

`/cww raftcore status` 现在带 `状态回写 N 次`。没有它，"倒计时在走但方块看着还是好的"
这种不一致在日志里完全看不出来，玩家也无从判断该不该去修。

## 3.7 帆与航行的第一手数据（M2 航行入口）

`tools/sail_probe.py` **8/8 + 1 条主动标为 INCONCLUSIVE**。这一节里有两条对玩法影响最大的读数，
以及一条我**拒绝假装通过**的断言。

### 结论一：帆在 Sable 的默认物理下不能推进（已证实）

Sable 默认维度物理 `basePressure = 1.0`，但压力是**只随 Y 变化的标量**
（`DimensionPhysics.createDefault` 用 `exp(-0.004·(y-seaLevel))` 拟合贝塞尔），
**没有风向矢量**。静风时帆相对空气的速度就是筏自己的速度，升力项推不出前进方向。

实测：静止状态下挂 5 块帆，6 秒内速率峰值 **0.011**（阈值 0.25）。
→ **帆是阻力面 / 龙骨，不是发动机。** 推进只能靠桨/螺旋桨（要客户端输入）
或我们自己往 dimension physics 里加风场。这条直接约束 P-01 的数值范式。

### 结论二：无动力时筏子只能滑 2 秒（已证实，影响最深）

同一冲量下的速率曲线：`0.332 → 0.047 → 0.007 → 0`，**约 2 秒就完全停住**。
→ 持续动力不是"可选优化"，是硬需求。12 分钟的局里要横跨几百格海域，
靠一次性冲量完全不可行。这条比帆的结论更该影响 M2 的排期顺序。

### 结论三：帆的阻力增量<b>没测出来</b>（我拒绝让它假绿）

第一版断言写成"带帆减速所需秒数 ≤ 无帆秒数"，结果两边都是 2 秒，**平凡通过**。
而挂帆后质量从 25.5 变 30.5，同一冲量下初速必然更低，直接比绝对值会把质量差异误读成阻力差异。
改成归一化比值后：无帆 `0.021`、有帆 `0.019`，差 0.02，落在噪声里。
→ 探针现在明确打印 `INCONCLUSIVE` 而不是 OK。**5 块帆的阻力作用在这个尺度上无法与噪声区分，
不据此下结论**；要判定就得加大帆面积或换更长的测量窗口。

### 顺带修掉两个会进生产的真 bug

1. **扫 `plot.getBoundingBox()` 把服务端冻住 5.2 秒**（日志 `Can't keep up! ... 103 ticks behind`）。
   原因：plot 局部坐标不是直觉里的 `-3..3`，而是相对 plot 网格槽位的大数
   （筏心 BE 的 `getPos()` 实测 `x=20481032`），包围盒跨度到几百万格，三重循环就是灾难。
   → 改成自己登记帆的局部偏移，数与拆只遍历这张小表。
   后果不止是卡顿：那次冻结让 RCON `stop` 失效、进程占死 25565/25576，下一个服务端起不来。
2. **恢复进 PLAY 后筏子绑定丢失**。sub-level 本身跨重启存活，但 `spawned`（队→筏 UUID）
   是运行时状态、没进快照，于是恢复的那一局"筏子在眼前漂着，而沉筏/挂帆/清理全找不到它"，
   命令只会回一句"队 0 没有筏"。→ 新增 `rebindFromWorld()`，按命名约定 `nbw_raft_<队>` 反查重认领。

另外还修了一条：打完一局的 LOBBY 快照里 `teams` 是空的，
而 `restore()` 的规格校验把"0 支队伍"当成非法快照拒绝——等于每打完一局重启都恢复失败。
空表现在按当前规格重建。

### 一个场地事实

`flat_test` 只是 y=148 的旱地基岩平台，**没有水**。筏子搁在上面不是船，
所以航行类测试必须先造海（探针里已加）。这也说明 M2 之后需要一个真带水的 arena，
对应 M3 的黑海，不能一直借 drill 的旱地平台测航行。

## 3.8 风推进（M2-5）—— 通过，并留下一条未结案

`tools/wind_probe.py` **11/11**、`WindModelTest` **11 个单测**（全量 129 个）。

### 风解决了上一轮那条硬结论

`cww wind set north 2.0` + 5 块朝北的帆，12 秒速率曲线：
```
2.768, 3.060, 0.475, 0.271, 0.270, 0.303, 0.292, 0.289, 0.290, 0.292, 0.291, 0.290
```
→ 末 4 秒稳定在 **0.29 m/s（≈5.8 格/秒）不掉回 0**。对比无动力时"2 秒完全停住"，
风确实提供了**持续动力**，不是又一次冲量。前两点 2.7/3.0 是上一次操作留下的残余运动，不是风的效果。

> **⚠ 2026-11-05 连续三次更正，最终版（前面两条都是我的错）：**
>
> 1. **本节最初的说法（"Sable 不采样外层世界的水、0.29 是水上终端速度"）不成立。**
>    读 `sable_rapier/.../rapier/src/buoyancy.rs` 后确认：`do_float` 逐格读**父世界**方块
>    （`chunk.get_block(...)` → `voxel_collider_data.volume`）给出 `10.5·体积` 的浮力，
>    `do_drag` 给出 `-速度·1.7·浸没体积` 的**水阻**。筏子能漂在水面、沉下去能落到底，靠的就是它。
>    → 所以"造海不改变航行读数"这句也是错的，它当时被我用来推导缺陷 B 的性质。
> 2. **我上一轮写的"真海上一路加速到 3.0~3.8 格/tick"是测量污染**：采样前我自己注入了
>    `sable physics impulse … 60`，那条曲线是**冲量余波的衰减**，不是风推的加速度。
>    重测纯滑行（不注冲量、只给初速）：**2.13 → 0.88 → 0.37 → 0.15 → 0.06 → 0.03 → 0**，
>    τ ≈ 0.27 秒归零 —— **水阻不但存在，而且很强**。
> 3. 帆数对滑行衰减几乎无影响（0/5/7 帆三条曲线重合，比值都是每 0.25s 约 ×0.41）
>    → **帆不额外产生水阻**（帆在水线以上，浸没体积不变）。所以"帆多更快"要的是
>    推力随帆数增长，这一项我们本来就有；缺陷 B 不是"缺阻力模型"。
> 4. **终端速度目前仍未量出来**：`wind north 2.0` 下 0 帆、1 帆都读回 `0.0000`，
>    5/7 帆在冲量余波消退后停在 ~0.11。而且 `test_sea` 半径只有 60、锚点在 0.8R=48，
>    筏子几秒就撞到海域边缘被卡住 —— **这块场地测不了航行终端速度**。
>    测法要求：`default_sea` 上取一条长直航段、每档复位到锚点、绝不注入冲量、对局没结束前测完。
> 5. **修好测法后的第一组可信读数（0 帆作对照、绝不注入冲量）**：
>    `3 帆 → 合力 6.0 → 1.546 格/tick ≈ 30.9 格/秒`；`0 帆 → 合力 0、速度 0.0000`（对照组过）。
>    **方向和"风推不过水阻"正好相反：现在的疑问是推力太强。** 31 格/秒意味着
>    半径 60 的 `test_sea` 撑不满 4 秒，半径 140 的 `default_sea` 也只能跑约 9 秒就到岸 ——
>    所以 5 帆、7 帆读回的 0 **是撞边卡住 + 对局超时把筏清场**（同一次 `step 9` 也因此在
>    `No sub-levels found` 上失败），不是物理结论。探针已相应改成"每档复位到锚点 + 对局掉了就重开"。
>    在这条被 `default_sea` 上的长直航复测推翻之前，**证据是反对去改 Sable 阻力代码的**：
>    水阻已经在（∝浸没体积×速度），要动的更像是我们自己的推力口径。

### 另外三条同时被证实

| 断言 | 实测 |
|---|---|
| 无风时帆不产生任何力（对照组） | 峰值 0.011 |
| **背风不产生反向力** | 朝北的帆遇南风，峰值 **0.001**（帆不会变成"倒车挡"） |
| 无帆的筏不受风力 | 队 1 全程 0.000（帆是受风面，裸筏只能靠桨） |
| 公平性：全局单值 | 两队读到完全相同的风 `('0.000','-1.000','3.00')` |

### 为什么风在我们这侧而不是 Sable 里

Sable 的翼型公式只用"相对空气的速度"，而它的维度物理只有 `basePressure`（随 Y 衰减的标量）
与 `gravity`，**没有任何风向矢量**。要让它有风就得改那段翼型计算，也就是 fork。
本项目原先的"Sable 只读不改"纪律已由用户于 2026-11-05 放开：**功能要确定与 Sable 关联来实现，
必要时直接调整 Sable 源码**，不要再在旁边另起一套平行自研。风放在我们这侧仍然是对的
（Sable 确实没有风向矢量），但下一条 #32（终端速度/水阻）要先去扫 Sable 自带的
`universalDrag` 与 `floating_materials` 摩擦系数，而不是先写我们自己的阻力公式。
附带好处：事件池里的风暴/顺风可以直接调 `WindService.set`，圈层风场差异以后也能加。

`SableRafts.push` 与 `sink` 的区别是刻意的：`sink` 是"变重"所以按质量成比例，
风是**真实外力**不乘质量——乘了会让风对大筏不公平地更强。

### `core_probe` 的夹具缺陷：已结案（19/19）

排查过程（每一步都推翻了上一步的结论）：
1. 先怀疑产品 → 不是：进度直方图显示活着时能推到 40/80/83。
2. 再怀疑伤害打死引导者 → 部分对：`damage 1.0 × 11` 确实把 c0 打死，死玩家不能引导是正确行为。
3. 降到 0.5 伤害并在第 4 步前 kill+spawn 复位 → **仍然失败**，进度卡在 19/160 每秒重来。
4. 真因：`player <名> kill` + `spawn` 会让 **Carpet 假玩家换 UUID**，
   而模拟引导绑的是旧 UUID，`getPlayer(旧UUID)` 永远返回 null → 每 tick 重新武装、约 20 tick 打断一次。

真实玩家重生**不换 UUID**，所以这不构成产品缺陷。但它暴露一条必须写下来的约束：
**引导绑的是玩家身份（UUID），实体被替换时引导该不该继续，是一个要有明确答案的设计问题**——
现在的行为是"绑不到就打断"，对真人是合理的（死了就该断），
但以后加"复活后继续引导"之类的需求时，不能想当然。

`core_probe` 的修复方式很清楚（每局用全新名字起假玩家，不复用被 kill 过的名字），
留到下一轮做，**这一轮不声称它通过**。

### 取证到的三条事实（都改了设计）

1. **筏子的浮力与水阻来自 Sable 逐格读父世界方块（我先前这条搞错了，见 §3.8 最终版更正）。**
   Sable 有两条路径：Java 侧 `FloatingBlockController`（按 `floating_materials` 材质查表，
   不读世界流体）+ **Rust 侧 `buoyancy.rs`**：`do_float` 用 `chunk.get_block(...)` 拿方块体积给
   `10.5·体积` 浮力，`do_drag` 给 `-速度·1.7·浸没体积` 水阻。实测纯滑行 τ≈0.27 秒归零，
   说明后一条对我们生效且**阻力很强**。→ 造海会改变航行读数；缺陷 B 不是"缺阻力模型"，
   而是"推力与水阻的比例没配过、且我们从没在能跑的场地上量过终端速度"。
2. **持票的 sub-level 不会被踢出物理管线。** `PhysicsChunkTicketManager:167` 对
   `collectForceLoadedSubLevels()` 里的 sub-level 走 `inhabitChunk` 分支，由 Sable 自己给外层区块下票；
   只有**没票**的才会走 `:183 moveToUnloaded`。我们的筏已经持 `nbw:round_active`，
   所以原计划的第二张 `nbw:arena_active` 票**取消**（会是恒真断言）。
   真机验证：把筏传到没有任何 forceload 的 (-1000,700)，14 秒后姿态仍读得到 `Y=63.05`。
3. **1.21.1 datapack 约定已核实**：目录是单数 `data/<ns>/function/`（FunctionLoader 常量池含
   `"function"`/`".mcfunction"`）；函数宏可用；`return` **只接受裸 `return fail`**，
   写 `return fail 0` 会让整个函数**静默加载失败**；mod jar 里的 `data/` 会被自动挂载（Sable 自己就这么发）。

### 缺陷 B：航速没有天花板 —— **已解决（2026-11-05，数值由代理标定、用户授权）**

> ⚠️ **本小节的数值口径已在同日被 §3.11 取代。** 这里的 `MAX_SAIL_SPEED = 0.45`、
> `headroom = 1 − (v/cap)⁴` 以及下面那张 0.156 / 0.336 / 0.394 / 0.419 的帆数曲线，
> 全部是 `linearVelocity` 的**瞬时峰值读数**，不是玩家看见的位移速度（同一状态位移只有约 1/22）。
> 这两个符号在代码里已经不存在，改由 `SpeedGovernor` + `RaftMotionService` 按位移闭环配平。
> 本节与下表只作历史与教训保留，**不要据此推玩法节奏**。

**做法**：`WindModel.FORCE_PER_SAIL` 1.0 → **0.2**（真机标定），新增 `MAX_SAIL_SPEED = 0.45` 格/tick
与 `headroom(v, cap) = 1 − (v/cap)⁴`，`WindService` 施力前按当前水平航速收力；读数行带 `上限/余量`。

**真机帆数曲线**（`sail_long` 赛制、0 帆做对照、绝不注入冲量、每档复位锚点）：

| 帆数 | 合力 | 终端速度 | 折算 |
|---|---|---|---|
| 0 | 0.00 | 0.000 | 对照组：无帆不受风 ✓ |
| 1 | 0.40 | **0.156** 格/tick | 3.1 格/秒 |
| 3 | 1.20 | **0.336** 格/tick | 6.7 格/秒 |
| 5 | 2.00 | **0.394** 格/tick | 7.9 格/秒 |
| 7 | 2.80 | **0.419** 格/tick | 8.4 格/秒，逼近但从未超过上限 0.450 |

即"帆多更快"成立、天花板生效，而且没把所有船压成同一个速度（软拐点的作用就在这张表上）。

**这条曲线差点被夹具废掉**：假玩家落在锚点的水里会**溺死**，某队全灭后
`RoundMachine` 判 `aliveTeamCount()==1` 提前结算、筏子被清场，于是第 2 档之后所有读数都是 0——
看着像"风推不动"，其实是"场上没有筏子"。修法全在夹具侧：假玩家加 `water_breathing`；
探针自写 `sail_long` 赛制（PLAY 900 秒；随包 `standard_12min` 的 PLAY 实测只有 45 秒，
而一次四档扫描就要 40 秒）；假玩家名比对改大小写不敏感（Carpet 回显会首字母大写）。
**教训：测航行的对局必须能活过整轮扫描。**

**没改 Sable**：水阻本来就在（`∝浸没体积×速度`），问题出在我们自己的推力口径，
按"完全确定和 Sable 关联来实现"的原则这次不需要动依赖。残留的加载开销另记 #35。

### 探针自身踩到的三个坑（都造成过假失败，值得记住）

1. `data get storage <store> rows` 在队列有 525 条时回包过大，**服务端直接掐断 RCON 连接**
   → 改成 `execute if data … rows[0] run data get … rows[0]` 只取队首。
2. `tools/rcon.py:_recv` 在连接被关闭时是**死循环**而不是报错，于是"掐线"表现为"探针无声卡住"；
   已改成抛 `ConnectionError`。
3. 同一连接上连着发"命令 + 哨兵"会被服务端掐线；单发 + `select` 只读已到达的包才稳。
4. **`Can't keep up! Running Nms` 的 N 是累计欠账，不是单帧时长。**我把这两个数混用过一次，据此立了一条根本不存在的『6.1 秒冻结』缺陷。判卡顿必须自己记 tick 间隔——`ArenaChunkLoader` 现在整局观测 `maxTickGapMs` 并在回收行打印（实测整局最大 65ms）。
   另外 `run/server-console.log` 是 Gradle 缓冲的，**别拿它的时间戳量耗时**。

| **划的人属于这队** | "这人不在队 0（他的队号=1）" | 少了它，敌队可以右键占满你的桨位堵人 |
| 一支桨一个人 | "没有空着的朝 SOUTH 桨台" | 五人挤一台桨不等于五份动力 |
| 一个人一支桨 | "正在划桨位 0，换桨得先松手" | 一个客户端对多桨位续包不能叠力 |

第二条与第四条是本轮补的：`hold` 原先在判归属之前就先找空桨位，
于是跨队的人收到的是"没有空桨台"这种误导性结论 —— 真正的拒绝理由被掩盖，探针也就无法证明闸门存在过。

### 本轮查出来的两个口径问题（都不是桨本身的错，但都会骗人）

1. **读数不等于位移，差约 22 倍。** 满员划桨 8.1 秒实际只走 **2.4 格（0.29 格/秒）**，
   而同一时刻的速率读数是 0.3207 格/tick（6.41 格/秒）。对照实验：给一个已知的
   `sable physics impulse 12` 之后，读数还有 0.0169，筏子实际只挪了 0.23 格。
   根因是我们每 tick 用 `applyLinearImpulse` 施力，读到的是施力后的**瞬时峰值**，
   而 Sable 的水阻在同一 tick 内就把绝大部分速度吃掉。
   影响面：`WindModel.MAX_SAIL_SPEED`、P-01 的"≈2/3/5/8 格/秒"、以及我写在注释里的
   "横穿 280 格约 31 秒"——**这些都按读数算过，必须用位移重标**（任务 #39）。
   探针已加了一条位移实测与"读数/位移"倍数的打印，这个偏差以后藏不住。
2. **同名 sub-level 残骸会让位置读数骗人。** 一次性配对实验里
   `sable storage find_all_sub_levels` 列出 **3 只 nbw_raft_0 + 3 只 nbw_raft_1**
   （多轮开局/重启/崩溃遗留）。按名字取位置与按 UUID 取速度会配到不同个体，
   表现正是"速率 0.1078 而漂行 0 格"。清理之后（1 只）同一读数下位移是 2.4 格，
   说明残骸确实是位置类读数的干扰源。`sable remove` 报 "Removed 3 sub-levels" 后
   `find_all_sub_levels` 仍列出旧条目，但**下次关档之后确实消失了** —— 删除是在存档时落盘的，
   我原本写成"不清盘"是过头的结论，已在任务 #38 更正。
   探针因此加了"盘上同名筏体数量"的打印，并在 >1 时把漂行标注为只作参考。

### 重启恢复：第一次"通过"是假象，清干净世界才看到真问题

第一轮跑 `oar_restart_probe.py` 时 after 段报"桨=2 自己回来了"，我据此差点写下"重启不用重新挂桨"。
把 dev 世界的同名残骸清掉之后（`sable storage find_all_sub_levels` 从 3+3 只降到 1 只）再跑，
同一套断言直接掉回 桨=0、"本局还没生成过筏"。**先前那条结论是被同号残骸撑出来的假绿。**

真问题在恢复时序上，日志顺序是决定性证据：

```
12:20:57  [raftgen] 重启重认领 0 艘筏；没找到：队 0 队 1
12:20:57  [state] 已恢复到阶段 PLAY（match=62，阶段内 130 tick，参战 2 人）
12:20:59  [oar] 桨位回填 team=0 slot=0 ...        ← sub-level 两秒后才载进来
```

`rebindFromWorld` 只在恢复那一刻调用一次，而那一次 Sable 还没把 sub-level 装进容器，
于是"恢复出来的这一局看不见自己的筏"：桨力、挂帆、沉筏、局后清理全都指向不到实体。
修复是把认领变成**可延后重试**：`RoundManager` 的 tick 里，对局进行中每 20 tick 检查一次
`RaftSpawner.needsRebind()`，还有队没绑上就重试（`rebindFromWorld` 本来就幂等：补 UUID + 绑沉筏 + 补票），
并把"这队没找到筏"的话术按队去重，避免每 20 tick 刷一行同样的缺失清单。

修复后实测（after 段 11/11）：

| 断言 | 结果 |
|---|---|
| 全程不调用 `oar rig`，`oar read` 仍是 桨=2 | 通过（身份来自 BE 的 NBT） |
| 回填的方向与 plot 偏移原样回来 | 通过：`dir=(0, 1)`、`(-3,1,-2)`/`(-3,1,-1)` |
| 重启后这队的筏被重新认领 | 通过：`队0 Y=63.84 质量=27.5`（比空筏 25.5 多出的正是 2 台桨） |
| 按回填偏移真能拆掉桨 | 通过：`拆掉 2 台桨台`，第二次拆报 0 台 |
| 划桨状态不跨重启 | 通过：在划=0（否则就是凭空多出动力） |
| 同号重复筏体必须吵出来 | 通过：6 行回填、4 次重复认领 → 2 行 ERROR（#38） |

**仍然没验的一条**："重启后仍然划得动"。对局进行中既不允许中途加入也不允许改队，
而 Carpet 假玩家重启后不是同一个 UUID，探针拿不到一个"已分配的划桨者"——这条留在 §6 的真人清单里。

## 3.11 航行控制器：把"航速"搬回位移口径（#39 已修，42/42）

### 为什么必须动这一层

§3.10 记下的是一个尴尬的事实：我们所有的航行数值都建立在 `linearVelocity` 的读数上，
而那是**每 tick 施完冲量后的瞬时峰值**。实测同一状态下峰值 6.41 格/秒、位移只有 0.29 格/秒，
差约 22 倍。02 §6 与 P-01 写的"几格/秒"是玩家能看见的位移速度，所以档位数值全线对不上。

P-01 里我自己推荐的那条"速度控制器"因此不是可选项，是唯一能把数值口径讲清楚的修法。

### 现在的形状

| 层 | 职责 |
|---|---|
| `domain/raft/SpeedGovernor` | 档位（纯位移速度）+ 比例控制律 + 每 tick 增量硬顶。纯函数，13 条单测 |
| `raft/RaftMotionService` | 每 tick 汇总各动力源的目标矢量 → 读位姿算实测位移 → 施**唯一一发**控制冲量 |
| `WindService` / `OarService` | 只登记"我要沿哪个方向、以多大位移速度走"，不再各自施力 |

单点施力是刻意的：帆与桨若各自闭环，两个控制器盯着同一个刚体、各看各的方向，
在临界速度上会互相打摆。矢量先相加再控制，抵消关系（2 南 + 2 北 = 不动）自然成立。

### 档位数值：02 §6 原表 ×2（用户 2026-11-06 指示"适当提高速度"）

| 档 | 02 §6 原表折算 | 原表的 2 倍 = 现在的目标 |
|---|---|---|
| 木桨（每人） | 2 格 / 6 秒 ⇒ 1/3 格/秒 | 0.0333 格/tick = **2/3 格/秒** |
| 帆（每帆每单位风强） | 3 格 / 6 秒 ⇒ 1/2 格/秒 @风强2 | 0.025 ⇒ 1 帆 @风强2 = **1 格/秒** |
| 筏级上限 | —— | **0.35 格/tick = 7 格/秒**（7 帆常态风正好贴着，风暴时被夹住） |

为什么先试过 ×3 又退回 ×2：×3 时上限没跟着动，结果 4 帆就撞在 0.25 的保险丝上，
"帆多更快"只剩前 3 块有效 —— 那是配平自己造成的玩法塌陷。提速必须**连同上限一起抬**，
而上限一抬，`MAX_DV_PER_TICK` 也要一起抬（稳态需要 dv ≈ 2×位移速度），
否则真正的天花板就成了限幅而不是上限（这一版是 0.35 / 0.8 成套）。
桨:帆 = 2:3 两边一起放大，比例关系没动。

### 控制参数是被实测定下来的，两次都推翻了我自己的推导

1. **GAIN=0.6（我第一版拍的）** ⇒ 4 人目标 0.0668 只跑出 0.0154。
2. **我据此推断"被控对象是无记忆的"** ⇒ 把 GAIN 提到 20 ⇒ **4 人那一档 8.4 秒飞出 1475 格**
   （读数 66.7 格/tick，还有一次 tick 落后）：启动瞬态把筏子甩出海城，离水后水阻消失，速度就地失控。
   这一条是本轮最贵的教训：**推导出来的植物模型不能当结论用**，而且没有斜率限制的比例控制器
   在这种系统上会做出不可收拾的事。
3. 于是加了 `MAX_DV_PER_TICK` 硬顶，再分两步实测：
   - 单次 `/sable physics impulse`（J=1 走 0.01 格、J=4 走 0.07 格）拟合出阻尼率 **0.11~0.15 /tick**；
   - 持续施力档由"dv≈0.066 而实测位移 0.0338"反推阻尼率 **≈2 /tick**。
   两者差一个数量级，**我没解释清楚为什么**。控制器每 tick 施力，所以按持续档配平，
   并把这条矛盾留在注释里，禁止后人拿单次那条当 k 用。
4. `X/T = G/(G+k)`，k≈2 ⇒ GAIN=18 应该落到目标的 90%。实测 0.0151 / 0.0167 = **90.4%**；
   档位抬到 ×2 之后（0.0333 目标）实测 0.0300 = **90.1%**，帆侧 1/3/5/7 帆的实测
   0.0450/0.1345/0.2239/0.3135 同样是目标 0.05/0.15/0.25/0.35 的 90% ——
   残差与档位大小无关，说明 k≈2 这个量在 0.03~0.31 格/tick 这段范围内是稳的。
   这是本轮唯一一次推导与实测对得上。

|---|---|---|---|
| 1 人 1 桨 | 0.0333 | 0.0300 格/tick = **0.60 格/秒** | 0.90 |

| 4 人 4 桨 | 0.1332 | 0.1201 = 2.40 格/秒 | 0.90 |

帆那一侧（`sea_probe` 第 8 步，风强 2.0，0 帆做对照）：

### 探针也跟着改了口径（否则它会绿灯着骗人）

- `oar read` / `wind read` 的 `速度=` 与 `速率=` 现在就是位移速度，峰值单列成 `峰值=` 只作诊断；
- 新增两条能失败的断言：**单次读数不得越过上限 1.5 倍**（GAIN=20 那次 runaway 就是被"只看均值"漏掉的），
  **8 秒位移不得超过 40 格**（4 人目标只有 1.33 格/秒）；
- 每条 `oar hold` 都要自证登记成功，不再只在最后看人数。

### 顺带查到并修掉的席位问题（#41）—— 但我一开始的归因是错的

**现场**：抵消那一档只有 3 个人登记上，`oar hold` 回一句"这人不在队 0（他的队号=1）"。
**我第一版的结论是"`cww start` 的赛制变更重分队覆盖了显式 force"**，并且已经写进文档、还立了 #41。
那个结论**是错的**：真原因是**幽灵席位**——
Carpet 假玩家被 kill 时不触发 DISCONNECT，而在场兜底 `sweepDeaths()` 只在 PLAY 跑，
于是上一局（尤其是中途崩溃/超时的那几次）留下的会话一直占着队席；
队 0 满 4 人后，`cww force` 走到 `assignTeam` 的 `target.isFull()` 分支，
回一句"队伍 X 已满"就把人留在原来的队里。我拿"重分队"解释，是因为那条审计行更顺手，
而没有去读 force 的返回值——探针同样没检查它，所以问题一路漂到"抵消"那一步才露头。

**修法（两处）**：
1. `RoundMachine.releaseAbsent(presentIds)` —— 只在局没开/已收场（LOBBY/ENROLL）时把
   "不在场"的会话连队席一起放掉，并返回带名字与队号的可读条目；
   PLAY 期间刻意不做，那里掉线要走席位倒计时（05 C22）。
2. `RoundManager.sweepLobbySeats()` —— 每秒一次跑在 PLAY-only 块之外，
   放掉就打一行 WARN：`报名期放掉 1 个不在场的席位（事件漏报兜底）：h1（队 0 席位已释放）`。
   在场列表的收集抽成 `presentIds()`，两处兜底共用一个"在场"定义。

**验证**：`tools/seat_probe.py` 8/8 —— kill 掉已分队的假玩家后，WARN 必须出现且点名此人此席；
重新上线后 `cww force` 必须成功。另外 `oar_probe` 现在每条 force 都自证返回值
（被拒就等一拍重试，仍失败直接判 FAIL）——这条断言才是本来就该有的东西：
按现在的代码，如果席位问题再犯，报错会停在"指派被拒"，而不是跑到"抵消没生效"那种误导性结论。

**仍然存疑的一条**（不是本次结论，别当已证）：赛制形状变化时 `ensureTeams()` 确实会把
成员的 `teamIndex` 清成 -1 再按 `leastFilled()` 重排，理论上也能挪动人。
本轮没有复现到它，所以 #41 保留为"显式指派是否应优先于自动平衡"的待裁决问题，
但**它不是这次故障的原因**。

### 还没验的

- **同规格筏航速方差 ≤5%**（P-01 承诺的竞技公平指标）：本轮只验了同一艘筏的档位线性，
  没验多艘同规格筏之间的离散度。
- **大筏（扩展过的甲板）的 α 是否还是 0.5**：现在这个 90% 残差是小筏实测，筏子变大后可能偏。
- 真人客户端的"看着快不快"：数值口径对了不等于手感对，这仍然在 §6。

## 3.12 建造规则：玩家建造走的是 Sable 的"存储坐标"路径（M2-6，55/55）

### 现场：M2 清单上那三条，开工前一条都没有

03 里程碑给 M2 写的是"建造规则：建造区、面积/方块数硬上限、只有本队可改"。
实际状态是 `Phase.allowsBuild()` 在 domain 里躺了好几轮，全工程只有 `RoundMachine` 的自检
引用过它一次；方块事件一个都没挂。也就是说 PLAY 阶段任何人可以拆任何人的筏——
这条比"能不能扩建"严重，属于没人管就一定会出事的那类。

### 源码取证：服务端递交的交互坐标，不是玩家眼前的世界坐标

整个设计押在这条链上（都在 `sable-main`，行号已写进代码注释）：

1. `mixin/clip_overwrite/BlockGetterMixin.java:104-131`：射线先用筏的 `logicalPose`
   `transformPositionInverse` 反投影进筏自己的空间，再在 `subLevel.getLevel()` 里求交，
   **命中结果就留在存储空间里返回**。筏子开出多远都是这个口径。
2. `mixin/block_placement/BlockPlaceContextMixin.java:81`：Sable 自己判"我点的是不是 plot"
   用的就是 `getContaining(level, clickedPos)`。我们跟着同一个入口，不另发明一套。
3. `mixin/interaction_distance/PlayerMixin.java:36-49`：`canInteractWithBlock` 已经把玩家眼睛
   反投影进筏空间比过距离，所以我们**不需要**再补一遍伸手校验（长按通道当年那条是自己写的，
   因为那条走的是我们自己的 payload，不是原版方块交互）。

版本事实（值得记下来，免得下一个人再找）：`fabric-events-interaction-v0 0.7.14 + mc 1.21.1`
**没有** `PlayerBlockPlacementEvents`。放置只能挂 `UseBlockCallback`；
破坏挂 `AttackBlockCallback`（起手就拦，挖掘进度条都不出现）
+ `PlayerBlockBreakEvents.BEFORE`（一次判定的真正边界，计数与留痕放这里）。

### 现在的形状

- `domain/construct/BuildRules`：纯函数。阶段 / 分队 / 归属三道前置门，加上建造区
  （水平半径 + 相对甲板的垂直窗口 −1..+7）、六邻接、方块数上限、设施数上限，
  以及"破坏不查建造区、筏心受保护"。13 条单测逐条把门，**每条都测"只差一个输入"的对照**。
- `construct/BuildService`：适配层。把服务端递交的存储坐标解析成（我的队、这块筏的队、
  plot 局部坐标），扫一遍建造盒，交给纯函数，再落回世界（FAIL + action bar 提示 + INFO 留痕）。
- `sable/SableRafts`：新增 `raftAt / accessorOrigin / plotBlock / neighborMask / scan`。
  上层看不到任何 Sable 类型，隔离层这条规矩没破。
- **判定与读数同一口径**：`scanRaft()` 是唯一的扫描入口，`cww build status`、
  `cww build check` 与真实点击判定都走它（这条是被自己的探针抓出来才改的，见下面第 3 坑）。
- **观测面**：`cww build status`（累计计数 + 每队方块/列/设施/加载区块）、
  `cww build last`（最近 24 次判定，带解析出的局部坐标）、
  `cww build check <asTeam> <onTeam> <place|break> <lx> <ly> <lz> [blockId]`（按坐标问判定，
  不写方块；越界/悬空/顶格这几条靠假玩家瞄是瞄不出来的）。

### 实测（`tools/build_probe.py`，55 条断言全从服务端读数取，不抄常量）

| 项 | 读数 |
|---|---|
| plot 存储原点（队 0 筏） | `(20481032, 128, 20481032)` —— 与海域坐标完全无关，"用世界坐标寻址筏内方块"到此有数值证据 |
| 初始筏扫描 | 方块 50 = 列 49 + 设施 1（筏心），加载区块 1 |
| **真实右键**（假玩家站 (−3.5, −1.6, 0)，yaw 90 pitch 25） | 方块 50→51，判定环解析出局部 `(−3,1,0)`；换 `check break` 那条路径读回那一格确实是 **Dirt**（甲板仍是 Oak Planks，所以这不是"整张表都读成方块"） |
| **真实左键** | 51→50，局部 `(3,0,0)` 读回 **Air**，列数 49→48 |
| 瞄准方向交叉校验 | 人站在哪一侧朝筏子看，解析出的局部坐标就必须同号那一侧；命中格必须落在半径 ±1 内 |
| 夹具图（半径 8） | 列 289 = 17×17、方块 290 —— 扫描盒 ±12 确实罩得住整张筏（这条专抓"上限只统计了建造盒"） |
| 方块上限顶格 | `maxBlocksPerRaft=301`，补 7 帆 + 4 桨到 301 后普通木板被拒并报 `301/301`；拆掉又放行（活读数，不是锁存） |
| 设施上限 | 顶格 8/8 时 `nbw:sail` 被拒、`minecraft:oak_planks` 仍放行；拆回 1/8 后帆又能放 |
| 阶段门 | SETTLE 与 LOBBY（筏在、队也对）都拒，原因都是"当前阶段不开放建造" |

回归：`oar_probe 42/42`、`seat_probe 8/8`、`sea_probe` 见 §5、单测 194/0。

### 这一轮我自己踩的六个坑，每个都能造成"看着对、其实错"

1. **`.gitignore` 的 `build/` 是不锚定的**：`src/main/java/dev/nbw/build/` 和
   `domain/build/` 整个不进版本库，`git status` 连未跟踪都不显示。差一点就提交了一个
   "少两个源文件"的 commit，而本地构建与测试还是全绿。包名改成 `construct`。
2. **`buildRadius = floor(sqrt(maxRaftArea))` 与字段名自相矛盾**：96 会放开 19×19=361 列，
   比"面积上限"大 3.7 倍。改成"不超过该面积的最大奇数边长"：96 → 半径 4（81 列 ≤ 96），
   49 → 半径 3，正好等于初始筏，语义成"这张图只许在原甲板范围内重建"，
   小面积自然收敛到 0，不需要 `area<=4` 特例。
3. **上限的扫描口径不一致**：判定用 ±(buildRadius+1)、读数用 ±12，于是 `maxBlocksPerRaft`
   实际只统计建造盒里的方块——大筏少算、上限偷偷变松。是探针那条"半径 8 的筏列数必须 289"
   把它抓出来的；现在三处共用 `scanRaft()`。
4. **`execute as <bot> run tp <bot> ~ ~ ~`**：`~` 取的是**命令源**（RCON 控制台）的坐标，
   不是执行者的。四个假玩家被整排拽到 `(400, 102, 400)`，于是我一度以为"放置不触发事件"
   是产品问题——那是我自己写的夹具在拆台。
5. **Carpet 的 `player <名> kill` 大小写敏感**：建出来的假玩家名一律小写，用 `u1408A0` 去 kill
   是对空名字打拳（不报错、也不掉线），四个人继续占着队席；下一支探针 `cww force` 就报
   "队伍 蓝队 已满"，看着像 #41 复发，其实是残留。**探针必须为自己清扫现场**。
6. **Brigadier 两条语法**：不带引号的 `string()` 不吃冒号（`nbw:sail` 被切成 `nbw` + 尾随数据），
   末尾可选参数得用 `greedyString()`；六层 `.then()` 写成一整条链时我把 `onTeam` 挂成了
   `check` 的并列子节点，`asTeam` 变成叶子，命令直接解析不动——改成每层一个命名 builder。

### 已知边界（都写进了代码注释，不是藏起来的债）

- **我们放行 ≠ 放得下**：实测筏体外沿那一格（局部 `(4,0,0)`）我们的门说允许，
  而 Sable 的 `BlockPlaceContextMixin.canPlace` 判它与筏体碰撞盒重叠，把放置拒了，
  玩家看到"什么都没发生"。这是体验问题、不是安全洞，但记录在这儿。
- **扫描盒固定 ±12**：比它大的筏会少算。正解是改读 Sable 自己维护的 plot bounding box
  （`MassTracker.build` 用的就是它），本轮没做，注释里写明了换法而不是换常量。
- **建造没有额外经济规则**：拿方块/掉方块都走原版，`maxBlocksPerRaft` 就是唯一的资源闸门。
- **`limits.buildYRange` 仍未接入**：它是世界 Y（62~80），建造区要的是"相对甲板几格"，
  两者不是一个东西，硬接一定错。垂直窗口现在是 `BuildRules.MIN_LOCAL_Y / MAX_LOCAL_Y`。
- **"每 9 格甲板 1 个设施位"没有实现**：按那个公式，7×7=49 的初始筏只有 5 个位，
  而我们现在一条 `cww oar rig 0 4` 就吃掉 4 个位，会立刻撞线并让既有探针全红。
  设施位与筏面积怎么绑是玩法决策（要连初始筏尺寸一起配平），留在 01 §4.2 待批。

## 3.13 初始筏削弱到 4×4，设施位改成每 5 格甲板 1 位（M2-7）

### 用户裁决两件事，第二件把我原稿的系数改了

- 初始筏从 7×7（49 格）**削弱到 4×4（16 格）**；
- 设施位不跟"随便摆"，而是**每 5 格甲板 1 位**（我 01/02 原稿写的是"例如每 9 格"）。

### 为什么一次"改尺寸"要动布局层

旧代码把甲板当成奇数方阵：`createRaft(radius)` 铺 `x,z ∈ [-r, r]`，帆铺在 `z=-3` 一排、
桨铺在 `x=-3` 一列。4×4 是**偶数边长**，这套写法根本铺不出 4×4（半径 2 会得到 5×5）；
更要紧的是把边长直接换成 4 之后，`±3` 那一圈设施格**落在甲板外面**——帆贴在空气上，
桨台挂在没有方块实体的格子上，一句动力都不会有（这类"看着挂上了其实没挂上"正是 §3.10 记过的坑）。

所以新增 `domain/raft/RaftLayout`（纯函数 + 单测）作为甲板几何的唯一来源：

- `deckStart(side) = -(side >> 1)`、`deckEnd = start + side - 1`（4 → `[-2, 1]`，含筏心所在的 0）；
- **帆取第 0、2、4… 排，桨取第 1、3、5… 排**（排从尾排往内数）——两类设施天然不撞格，
  旧布局在 `(-3,-3)` 那一格其实是撞的；
- 筏心格 `(0,1,0)` 谁都不许占；`sailCapacity(4)=7`、`oarCapacity(4)≥4`，
  也就是 02 §6 的 7 帆档与 4 桨档在削小后的筏上**仍然摆得下**（这条如果不成立，
  "小筏"就等于"不能航行"，那是玩法塌陷而不是平衡）；塞不下时返回 null，
  由 `Sailing`/`OarService` 报失败，绝不静默少挂。

`SableRafts` 铺甲板、`Sailing` 挂帆、`OarService` 挂桨现在都问同一处要边长
（`RaftSpawner.deckSide()`）。配置字段相应从 `limits.initialRaftRadius` 换成
**`limits.initialRaftSide`**（校验 0..17，0=用默认 4）——用半径表达不了偶数边长。

### 设施位这道门从"数天花板"改成"数面积"

`BuildRules.facilitySlots(columns, maxFacilities) = min(maxFacilities, columns / 5)`。
面积基准取**占用列数**而不是方块数：往上盖两层楼的方块数会翻倍而 footprint 不变，
用方块数等于"盖楼白送设施位"。筏心自己算 1 个设施，所以 4×4 的开局只有 2 位能用——
这就是 01 §4.2 想要的"扩筏 vs 建军械"抉择，现在它是真的在约束玩家。

### 实测

| 项 | 读数 |
|---|---|
| 初始筏（默认图） | 列 16 = 4²，方块 17 = 16 甲板 + 1 筏心，设施 1，**额度 3/8** |
| 顶格 | 补 2 面帆到 3/3 → `nbw:sail` 被拒并说"每 5 格甲板才给 1 位（现有甲板 16 列）"；同格放 `minecraft:oak_planks` 仍放行 |
| 夹具图（10×10） | 列 100、额度 8（被 `maxFacilities` 夹住，天花板确实会生效）；`maxBlocksPerRaft=112` 顶格时普通方块报 `112/112` |
| 发筏质量 | 9.0（16 × 0.5 + 筏心 1.0），`raftgen_probe` 18/18 |
| 桨位跨重启回填 | 偏移动回到 `(-2,1,-1)`、`(-1,1,-1)`，`oar_restart_probe` before/after 4/11 全过 |
| 回归 | `build_probe 60/60`、`oar_probe 43/43`、`sea_probe 39 PASS`（帆档 0.0450/0.1346/0.2239/0.3134，已回到削弱前的曲线）、`raftgen 18/18`、`sink/core` 全过、`oar_restart before/after 4/14`、单测 200/0 |

### 削弱之后暴露出来的真问题：小筏大帆会横着走

`sea_probe` 的帆档位扫描先报了两个错：终端速度不再随帆数单调（1/3/5/7 帆 =
0.0447/0.1273/0.0492/0.1059），以及**南风下位移 z 分量是负的**。

**我第一版读数作废了，原因在夹具**：每档只用 `sable teleport` 复位，而它只挪位置不消速度
——实测每档开头还带着上一档的速率 4~5 格/tick 和几十度的角速度。量到的是残留翻滚。
改成"反复复位并等到速率 < 0.004 再计时"之后，数字才算属于这一档（`sea_probe.terminal()`
与临时脚本都按这条改了；这条如果不写下来，下一个人还会拿同一组假数字下结论）。

静止基线下重测（南风 2.0，5 秒窗口，侧移/顺风位移比）：

| 帆数 | 4×4 旧取格顺序 | 4×4 中心交替 | 7×7 旧取格顺序 |
|---|---|---|---|
| 1 | 0.108 | **0.018** | 0.012 |
| 2 | 0.390 | **0.019** | 0.087 |
| 3 | 1.129 | 0.191 | 0.252 |
| 4 | 2.679 | 0.448 | 0.547 |
| 5 | 11.804 | 0.339 | 1.100 |
| 7 | 0.485（Yaw −161°，在打转） | 0.097（仍在打转） | 1.865 |

两个结论：

1. **取格顺序是主因**。旧顺序"从边到边"扫，部分填充时帆的面积中心整排偏到一舷，形成偏航力矩，
   筏子顶风横爬。改成**从甲板中心往两边交替**（`RaftLayout.balancedOrder`）后，
   1~2 帆的侧移降到 2% 以内，5 帆从 11.8 降到 0.34。这条现在是不变量：
   `everyPrefixStaysWithinHalfACellOfTheDeckCenter` 逐档检查"任意前缀的面积中心离甲板中心
   ≤ 半格"（奇数格因为要跳过筏心所占那格，容差放宽到一格，测试里写明了为什么）。
2. **剩下 3 帆以上的不稳定，玩家够不着**。设施位规则（每 5 格甲板 1 位、筏心占 1 位）
   把 4×4 筏的帆数天然压到 2，而 2 帆实测航向干净；比例上帆的总质量也≤船体质量的 ~20%
   （旧 7×7 + 7 帆是 29%）。也就是说"小筏大帆会打转"正好是这道规则要挡在门外的组合，
   不是要额外补的机制。`sea_probe` 新增 8b 段专门把这条可玩配置钉住（侧移比 ≤0.10）。
   帆档位扫描（1/3/5/7 都要合法）因此改用边长 7 的夹具图 `test_sail7`（坐标与 `test_sea`
   一致，不需要重新建海）。

**没有做的（也不该顺手做）**：想让小筏也能挂大帆，就得给船体加稳向/舵面之类的恢复力矩，
或者把帆的受力点降到水面附近——那都是新机制，需要用户批准，不在"削弱初始筏"这条指令里。

### 又一处产品缺口：报名上限跟着"上一次装载的赛制"，而不是"这一局要用的赛制"

连着跑探针时 `oar_probe` 报了几条 `队伍 赤队 已满`。分诊下来既不是布局也不是 #41 复发：
上一局用的是 2×2（容量 4），机器里的 `RoundConfig` 就还是 2×2，而 `cww start` 要求
"先有下限人数报名才肯开局"——于是 2×4 赛制的第 3 个玩家起就被 `isFull()` 拒掉。
**报名阶段用旧规格，开局又要求先报满，两个条件互相卡住**；真实运营里同样成立：
管理员永远没法把对局从小规格换到大规格。

修法是补一个本来就缺的命令，而不是让探针绕过去：

- 新增 `cww format reload <id>`：只在没在打局的时候用（与 arena 换图同一道闸门），
  装载并校验赛制、把 `RoundConfig` 换过来，不开局；回显带规格/下限/容量便于核对。
  `loadConfigs` 的约定是"成功返回 null"，这里第一次写成了把 null 当消息打印，已改。
- `sea_probe.wait_clean_lobby(p, fmt=...)`、`oar_probe`、`build_probe.start_match`
  都在拉人之前先 reload 自己的赛制。

### 顺带修掉的几处探针自踩（都不是产品缺陷，但都会造出假红或假绿）

`oar_probe` 一上来报 `队伍 赤队 已满`：上一支探针（`build_probe`）的 4 个会话还挂在 2×4 的队席里。
根因链和 #41 一样——kill 掉的假玩家不触发 DISCONNECT，而局后清理是按"参战者实体"做的，
实体早没了就一个都处理不到，会话要等报名期兜底（约 1 秒一次）才放掉。
`oar_probe` 原来只等 `phase=LOBBY`，没等 `queue=0 teams=0`。现在加了公共前置
`sea_probe.wait_clean_lobby()`，探针之间不许再靠时序运气跑。这一轮又加了四条：

- **假玩家 kill 要用小写名**：Carpet 建号时统一转小写，用 `u12A0` 去 kill 是对空名字打拳
  （不报错也不掉线），四个人继续占着队席。
- **取证要带日志游标**：`seat_probe` 原来用 `re.search` 在整份日志里找"释放席位"那行，
  抓到了 `build_probe` 留下的 `u5707a0`，报了假 FAIL；现在先记字节偏移、再按名字匹配。
- **`sable teleport` 不消速度**：`sea_probe.terminal()` 原来固定 `sleep(2)` 就计时，
  现在改成"反复复位并等到速率 < 0.004"。改之前那份帆档位数据全是上一档的残留翻滚。
- **重启探针两段共用一条正则**：`before` 段自己抄了一份、漏掉 `dir=(0.0, 1.0)` 的括号，
  `offs_before` 于是恒空，`after` 的比对变成"空对空"（还顺手踩了一次分组序号位移：
  正则加了 dir 的两个捕获组之后，格子下标从 3,4,5 变成 4,5,6）。
  现在改成回写比对：重启前实测登记的格子进交接文件，重启后必须一模一样——
  抄死坐标的那版在筏尺寸一变之后会红得像是回填坏了。

### 已知边界与后续（都记在这儿，不留暗债）

- **02 §5 的"每 1 格甲板 = 4 木 + 1 布"还没接**：目前扩建不消耗任何资源，
  设施位额度是唯一的扩张约束。等 M3 的物资/生产系统一起做。
- **`maxRaftArea=96` → 建造区半径 4 → 最大 81 列**，而 5 格/位的额度要到 40 列才满 8 位：
  也就是说这套数值自洽，但如果以后想让大筏再多设施位，得连 `maxRaftArea` 一起抬，不是单改系数。
- **01 §4.1 的"队伍物资箱"仍未实现**（开局不发物品），这条一直在待批 A1 里。

## 3.14 落水与扒边自救（M2-8 第一段，rescue_probe 18/18）

### 批准到哪一层

01 §8 里 `[已批准]` 的只有"可自救 + 队友可救"这个原则，细则（2 秒攀爬、体力门槛、
伸手/抛绳、水中伤害衰减）都还挂着 `[新增·待批 A7]`。所以这一段只落地了**自救**，
并把每一条没做的都写清楚，不让代码替玩法做决定。

### 先说一条"看起来能移植，其实不能"的结论

Sable 有 `mixin/climbing_sub_levels/LivingEntityMixin`，它把 `onClimbable` 的判定反投影进
sub-level 找 CLIMBABLE 方块——这正是"筏上梯子可爬"，按"能移植就不自研"应该直接用它。
但它的条件是 `state.is(CLIMBABLE) && SablePlatform.INSTANCE.isBlockstateLadder(...)`，
而 Fabric 侧那份实现直接 `return false`，注释写着 "handled already for fabric"
（`SablePlatformImpl.java:20-22`）。这句话是别人对自己的说明，不是我们的实测，
所以**没有依赖它**：现在的扒边是我们自己的服务端状态机。
真要换成梯子，得先在实机上证明筏上的梯子能爬（已进 §6 真人清单）。

### 翻过车的三处，共同点是"不报错，只是永远判不够"

1. **两套"局部坐标"不是一个东西。** 方块交互事件递交的是**存储坐标**（量级 2×10^7，
   换算局部要减 `getCenterBlock()`，建造规则就是这么算的）；而实体的世界坐标过
   `logicalPose` 的逆变换之后**已经是以甲板中心为原点的局部坐标，再减一次中心就错了**。
   写错的表现不是异常，而是"人明明贴着船壳，服务端算出间隙 28,966,064 格"，
   于是整条自救静默不生效。现在 `rescue_probe` 第 1 段专钉这件事：把人精确放到筏的位姿原点上，
   间隙必须 0.000、局部 x/z 必须≈0（实测 0.000 与 (0.04, -1.22, 0.04)）。
2. **攀爬不能按"每 tick 抬固定格数"算。** 第一版是每拍抬 `1.3/40` 格，实测在水里 2.6 秒
   只净涨 **0.016 格**——下沉几乎把抬升抵消干净，"2 秒回筏"于是由水的参数决定。
   现在 GRAB 那一拍钉住起点 Y，之后每拍把人放到 `climbY(baseY, 甲板面, tick)` 的插值位置：
   泡多深只影响起点，终点一定是甲板面，时序仍然只由 `CLIMB_TICKS` 说话。
3. **"在水里"只能是起爬的门槛，不能是持续爬的门槛。** 人爬的过程中必然离开水面，
   一路要求在水里就会半路弹回水里重新抓——实测"扒住 3 次才上筏 1 次"、终点 Y 卡在水面线下方。
   改成"已经在校爬状态就豁免水条件"之后一次爬完。

### 实测（`tools/rescue_probe.py`）

| 项 | 读数 |
|---|---|
| 坐标口径 | 人放到位姿原点 → 间隙 0.000、局部 (0.04, -1.22, 0.04)（y 偏是假玩家穿甲板漂下去，不是换算错） |
| 攀爬过程 Y 采样 | 61.69 → 63.73（+1.97 格），甲板面 Y=64.02；连续 8 个采样高于起点 |
| 时序 | 一次 GRAB + 一次上筏，`上筏` 计数 0→1，在 2.6 秒窗口内完成 |
| 门 | 离壳 8 格判够不着（伸手 2.5）；别队的人贴到队 0 船壳边仍判 62.69 格（他够的是自己队的筏）；LOBBY 里 `hold` 不推进任何计数 |

### 这一段刻意没做的（都留在 01 §8 待批 A7）

## 3.15 伸手救援 + 长按通道的坐标空间（M2-8 第二段，rescue_probe 44/44）

### 批准到哪一层

01 §8 里那句"可自救 + 队友可救"当时欠的是细则。**2026-11-06 你裁了三条**，这一段照这三条落地：

1. **动作在救援方**：救援方长按 1 秒（20 tick）把人拉回筏上，这一秒他的手被占用；
2. **被救者不需要任何输入**：只要"在水里 + 够得着自家船壳"；
3. **救援方的资格只判到被救者的距离**，不判他自己落不落水、站不站得稳。

**待批的两个数**（表里没有，是我为了让判定可测而定的几何）：
伸手上限 `HAND_REACH = 3.5` 格（= 被救者还能自己扒到的 2.5 + 探身 1.0），
落点从船壳棱往内缩 `LANDING_INSET = 0.75` 格（玩家碰撞箱半径 0.3，踩在棱上会被筏子起伏挤回水里）。

顺带查出一条压着三条玩法的缺陷，所以这一段比原计划大：**长按通道的可达距离用错了坐标空间**。

### 缺陷：筏上的每一个长按都被判越界（实测钉死）

`nbw:hold` 包里的 `BlockPos` 是 sub-level 的**存储坐标**（实测量级 2×10^7），
而 `NbwNetworking` 原来算的是 `player.getPos().distanceTo(pos.toCenterPos())`
——父世界的玩家坐标（量级几百）比存储坐标，距离恒为天文数字，`HoldPolicy` 于是**一律判 REJECT**。
Sable 自己从不裸比这个数：它把玩家眼睛反变换进 sub-level 那一帧再比
（`mixin/interaction_distance/PlayerMixin.java:38`），射线也是先反投影再求交
（`mixin/clip_overwrite/BlockGetterMixin.java:116-124`）。

`cww net probe`（这一版新增的取证命令）打出来的两个口径：

| 口径 | 实测 | 判定 |
|---|---|---|
| 父世界直算 | **28,964,583.3 格** | REJECT |
| 甲板局部帧（眼睛 `worldToLocal` vs 目标 `存储−plot中心`） | **5.06 格** | KEEPALIVE |

后果面比救援大得多：**筏心修复、桨台推进、扒边续包**三条真客户端长按全都不生效。
之所以一直没暴露，是因为这三条的探针全都走 `cww ... hold` 模拟入口，那条路径不经过这道距离闸门；
而右键那一下走原版 `OarBlock.onUse`，它拿到的 world 就是方块所在的那一层，所以是对的。

> **我有一条归因被实测否掉了，写在这儿以免下一次又被当成结论用**：
> 我原本推断 `player.getWorld().getBlockEntity(存储坐标)` 也一并失效（以为 sub-level 方块不活在父世界）。
> 实测 `父世界BE=OarBlockEntity` —— **读得到**。源码也对得上：
> `ServerSubLevelContainer.java:152` 是把父 `ServerLevel` 直接交给 `ServerSubLevel` 的，
> 那些方块物理上就存在父世界的那片存储区域里。
> 所以"认方块"那条分派一直是对的，**坏的只有距离**。这一条我按实测改回原样，没有多修一层。
> 同理，客户端预筛（`client.world.getBlockState(准星坐标)`）**也不是恒读空气**：
> 放宽它只是因为"旱着的救援方指着的是一个普通甲板方块"，原来的白名单（桨台/残骸筏心/水里实心格）
> 根本不含这个动作。

新命令面（就是为这个缺口准备的，RCON 与 Carpet 都造不出真客户端的准星）：
`cww net probe <玩家> deck <队>` / `oar <队> <位>` / `at <x> <y> <z>`
——同一个人、同一格，把两种口径的距离与判定、以及方块实体读不读得到，原样打出来。

### 两条被"拉回这个动作本身"否定的门槛

第一版伸手救援**一次都没成功过**，症状是"拉回恒 0、伸手作废一路涨、被救者 Y 只爬到 62.79（甲板面 64.02）"。
查下来是两条门槛在过程中自己把自己判废：

- **在水里**：人往上抬必然离开水面 → 只作为**起拉那一拍**的条件（`ClingRule` 当年在同一处栽过，见 §3.14）。
- **伸手上限**：把人往甲板方向拉，他会离**泡在筏外**的救援方越来越远——实测距离从 2.30 涨到 3.56，
  第 13 拍被自己的 3.5 上限判废。也就是说这条也只能判开始：**一旦抓住，1 秒之内不许因为距离变化松手**。
  落点是每拍按筏的**当前**位姿换算的，所以筏子在这 1 秒里开走了，人也是被拉到那时的那一格，
  不存在"拉向一艘已经不存在的筏"。

`ReachRule` 因此有两扇门：`denyReason`（起拉）与 `denyOngoing`（继续），
差集只有这两条，其余（阶段、筏在、同队、不判自己、还扒得着自家船壳）一条不减。

### 顺手修掉的一条已确认缺陷：攀爬只抬 Y，人会停在筏旁

自救那套插值原来只改 Y，X/Z 一动不动。在离壳 2.5 格内扒住的人爬到顶，
是站在筏子**旁边**两格半的半空里，下一步掉回海里——01 §8 说的"爬回筏"根本没兑现。
现在起点与终点都钉在甲板局部帧里，终点是 `landingLocal` 夹进 footprint 内缩 0.75 的那一格，
每拍用新的 `SableRafts.localToWorld`（`worldToLocal` 的正变换）换算回世界坐标。

量法用的是**人到筏中心的水平距离**（不采信服务端自己说的落点）：
假玩家站不住筏面，只会竖直穿甲板沉下去，所以水平那一维没被夹具污染。

| 那趟 | 起点水平距离 | 落点水平距离 | 半宽 |
|---|---|---|---|
| 队友拉回 | 3.01 | **1.28** | 2 |
| 扒边自救 | 2.33 | **1.28** | 2 |

服务端记的落点也一致：`拉回筏上（20 tick，落点本地 (1.25, 1.00, -0.06)）`，
±1.25 正好是 2 − 0.75 的边界，高度 1.00 = 甲板面。

### 按裁决不加限制带来的两条已知代价（等玩法单独裁，我没偷偷改）

- 两个都溺水的队友可以**互救**，而且互救（1 秒）比自救（2 秒）快；
- 正在自己扒边往上爬的人，同时还能当救援方去拉别人。

旁边若有合格被救者就会被顺手拉上来 —— 这是"复用同一条长按通道"的直接结果。

### 探针夹具上踩到的两条（都造成过假失败）

1. **起服务端时不要把 stdout 重定向到别的文件**：`seat_probe` 的证据通道是

### 长按输入通道（M2-4 欠的那一半，M2-8 才真的能用）

真人长按右键喂进引导判定：`net/HoldPayload`（C2S，只有目标坐标 + active 标志）、
`net/NbwNetworking`（服务端 codec + 接收器）、`client/HoldInputClient`（按住每 2 tick 续包，松手补一刀），
判定口径放在 `domain/net/HoldPolicy`（8 条单测）。服务端侧起服验证：
`[net] 长按输入通道已注册：nbw:hold（可达上限 8.0 格，窗口 4 tick；去向=筏心修复 + 桨台推进 + 救援；距离一律在甲板局部帧量）`，
专用服务端没有因客户端类而崩。

**M2-8 补上的关键一条**：这条通道的可达距离原来是拿父世界玩家坐标去比 sub-level 的存储坐标，
筏上每一个长按都被判越界（实测 28,964,583 格），所以现在距离一律走 `HoldPolicy.localDistance`
在甲板局部帧里量，并新增 `cww net probe` 把这个口径变成可断言的读数。详见 §3.15。

**这一版 API 的考古结论，别再来一遍：**

| 事实 | 依据 |
|---|---|
| yarn 1.21.1 **没有** `PayloadTypeRegistry` / `playC2S` 在 MC 侧；注册表在 **fabric 自己包里**：`net.fabricmc.fabric.api.networking.v1.PayloadTypeRegistry.playC2S().register(Id, PacketCodec)` | fabric-networking-api-v1 4.3.1 javap |
| **codec 注册与接收器注册是两件事**，只注册接收器则服务端解不出包 | 同上 javap 签名 |
| `ServerPlayNetworking.registerGlobalReceiver(CustomPayload.Id<T>, handler)`；`Context` 只有 `server()/player()/responseSender()` | javap |
| `PacketCodec.of` 的编码器是 **`ValueFirstEncoder`：值在前、buf 在后**，与 Mojang `StreamCodec` 参数顺序相反 | 编译报错 "无法将方法 of 应用到给定类型" 后查 `za → ValueFirstEncoder` |
| 内联 lambda 写在 record 的静态字段初始化里会让 javac 推断错参数（报 `找不到符号 p.pos()`），用具名静态方法即可 | 实测 |
| 服务端类里不许出现 `MinecraftClient` 等客户端类，否则专用服务端 `NoClassDefFoundError`；故拆 `client/HoldInputClient` | 结构约定 |

**仍未验证的部分**：包真的从客户端到服务端这一段（假玩家发不出自定义包），要真人客户端试——见 §6。

- **重启后由已分配的真人继续划桨**：探针拿不到"已分配席位"的人（对局中禁止中途加入与改队，假玩家重启后 UUID 还会变），所以只验到"桨位表能自己回来 + 筏子能重新认领"，没验到"人回来接着划"
- **筏子到底走了多远**（#39）：实测读数与位移差约 22 倍，玩家视角可能看到的是"筏子几乎在原地漂"。这条必须由你在真机上给个判断：现在的推力是要抬到"看着在走"，还是接受慢速并把玩法节奏按慢速重排
- **真客户端长按筏体外壳扒边**（§3.14）：状态机、时序、四道门、伤害打断都已用假玩家验过，

  与客户端预测之间会不会打架（橡皮筋、顿一下），探针看不见
- **真人伸手救队友**（§3.15）：时序、配对、拒绝与打断都验过，但要你手上确认三件事——

  ②伸手上限 **3.5 格**是猜的，真人站在筏边伸手，实际能救到多远的队友才不觉得莫名其妙；

- **筏上的梯子到底能不能爬**（§3.14）：Sable 那个 mixin 在 Fabric 侧的平台判定直接返回 false，
  所以现在没依赖它。如果你实机发现筏上放梯子能正常爬，就把扒边换成移植那条，别留两套机制

1. 真客户端那个长按包**到达服务端**这一跳本身：`cww net probe` 只能证明"包到了会怎么判"，
