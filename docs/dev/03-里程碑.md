# 03 · 里程碑与验收（新计划）

> 与旧计划的根本差别：**M0 的全部内容是"证明 Sable 可用"**，玩法代码一行不写。
> 人日按单人开发 + 我自测估算，置信度中等；M0/M1 较准，之后 ±40%。

---

## M0 · Sable 可行性验证（**5–9 人日**）

交付：一个只含"造筏 + 移动 + 交互"的最小工程 + `docs/dev/M0-RESULTS.md`（逐条结论 + 证据）

按 `02-风险与M0验证.md` §4 的 M0-1…M0-10 顺序执行。

**Gate G0（不过就不进 M1）**
- M0-1～M0-3 必须全绿（能起服、服务端可用、拿到可用 API）
- **M0-4 手感由你判定**（我给视频与数据，不自作结论）
- M0-5～M0-6 至少有一条可接受的实现路径（含"需要变通"的 B 级）
- 任一失败 → 回到 `00-决策与版本.md` §2 重选（首选退路：1.20.1 + Eureka/VS2）

产出物还包括：**Sable 适配层的接口草案**（我们到底需要它的哪几个能力，写成代码接口，后续只实现不返工）。

---

## M1 · 对局骨架（**6–10 人日**）

与 Sable 无关的部分先做扎实（旧计划里这部分已被验证可行，可移植思路与测试）：

- 回合状态机：六阶段 + 显式转移表 + 审计 + 每次转移落盘
- 配置层：arena / format / lobby JSON + **8 条校验 + 失败拒绝加载并归档**（校验失败不自动纠正是硬要求）
- 分队与席位、传送进出、胜负判定占位、结算与回大厅
- **局后状态清理断言**（含"复活会替换玩家实体对象"的附件迁移）
- 命令树与权限、RCON 无人值守回归脚本

**Gate G1**：连开 5 局无残留、重启能恢复到当前阶段、坏配置不崩服。全部由脚本断言，不靠肉眼。

---

## M2 · 木筏玩法闭环（**8–14 人日**，取决于 M0 结论）

- 每队一筏：初始 sub-level 筏体生成、出生等角分布
- 建造规则：建造区、面积/方块数硬上限、只有本队可改
- 航行：动力（桨/帆/电鳗发电机）→ 调 Sable 移动；速度/转向规则由我们定义
- 筏心与沉筏：血量、30s 倒计时、反偷家保护（有幸存者时破拆 ×0.25）、重修一次
- 落水与救援：扒边自救、队友伸手/抛绳（**若 M0 证明 Sable 表面判定可用，就基于它做**）
- PVP：伤害走我们自己的武器表

**Gate G2**：真人可玩一局并分出胜负；手感、建造、救援三项有明确反馈。

---

## M3 · 黑海 + 物资 + 竞技核心（**10–16 人日**）

- 圈层压缩（纯函数 + 表驱动单测）、圈外伤害与附加效果、预告与可视化
- 环带品质、物资刷新、防蹲点、可见性
- 埋点与配平回路（局时长、首战时刻、生产参与率）

**Gate G3**：每局都在 15 分钟内结束且最后 3 分钟有交战；≥70% 对局使用过生产设施（否则数值回炉）。

---

## M4 · 生存养成（**8–13 人日**）

- 营养/水分/受伤（+可选失温）、HUD 状态条
- 生产链 6 设施 + 筏级功率池（不做电路）
- 武器 12 件全量接入 + 平衡护栏（禁用原版武器合成配方）

**Gate G4**：状态不得单独致死满装备玩家（0 例）；生产链有真实价值。

---

## M5 · 幸存者 + 事件 + 运营（**10–16 人日**）

- 幸存者 6 职业（M0 若证明 Sable 能承载实体随动，则工作量下降）
- 事件池 6 个（全场同等生效 + 提前预告）
- 战绩持久化 + 外观解锁（无数值）、观战空投、赛后面板、快捷指令
- 部署运维：整合包依赖清单、版本握手、灰度与回滚、备份恢复演练

**Gate G5（开服标准，逐条签字）**：48h 耐久无异常；崩溃恢复演练 3 次；边界用例全过；反作弊与泄露用例全过；回滚演练一次成功。

## 开发纪律（上一轮踩过的坑，这次写死）

1. **一次一个模块，做完做透再下一个**；自动化任务与人工会话不得同时写同一仓库。
2. **假玩家只验证服务端数据与逻辑**，凡依赖客户端同步的表现（随动、传送、视角、手感）必须真人判定。
3. **提交前核对 `git status` 与 `git diff --stat`**，提交信息必须与实际改动一致。
4. **起服前先探端口**（25565/25575），收尾必须干净停服。
5. **结论必须带证据**（测试数、日志行、RCON 回包、视频），区分"已核实"与"推测"。
